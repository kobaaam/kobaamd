## 良かった点

- **wiki-derived `postmortem-patterns §18` が reviewer 側で機能**: 1st review_pr が「観測機構の変更には観測機構自体の smoke test を初手で含める」を直接引用して fail 判定を出し、AC4 未検証を `rework` に分類した。KMD-153 で言語化したパターンが、その後の review で運用ルールとして実機適用された最初の事例
- **AC4 の rework 指示が極めて具体的**: 推奨 A（手動検証の手順 + ログ提出）/ 推奨 B（bats 化）まで列挙。実装側は迷わず推奨 A を実施し、22 分で再 PR に到達。「rework 指示の具体性が rework 速度を決める」を裏付け
- **AC4 検証ログが「fail 解消の証拠」として機能した**: Run 1 (cache miss, 27s) / Run 2 (cache hit, 0.5s, subagent 起動 0 回) という定量比較が PR コメントに残り、2nd review_pr が APPROVE を機械的に判定できた。「検証ログを PR コメントに残せ」が auto-pipeline の品質ゲートとして効く
- **副次バグ（stderr の `"section-context-check: section-context-check:"` 二重 prefix）を rework 中に発見・同梱修正**: 検証中に観測したノイズを 3 行修正で `654c3bc` として同時 commit。観測機構の検証 → 観測機構自体の cosmetic bug 発見 → 同 PR で解消、という波及が自然に起きた
- **review_security が PR の本質を踏まえて軽量モードで通した**: 「観測機構 + 内部リファクタリング」と一次分類し、`§12` の重い AC を適用範囲外と明示。INFO 1 件（temp file trap 不整合）は本 PR を block せず KMD-175 に carve、という判断ロジックが KMD-153 の learning 通りに機能している
- **auto-carve が `親→子→孫` の三段で機能**: KMD-150 → KMD-155 → (KMD-174 + KMD-175)。各 PR が独立サイクルで完了し、上位の merge を block していない
- **構造的保証を AC に組み込んだ**: 「両経路が共通ヘルパ `content_hash` / `cache_store` / `cache_lookup` を呼ぶ構造」にしたことで、legacy ↔ subagent 跨ぎ実機テストが API key 不在で実行できなくても整合性が**構造的に保証**される設計。テストで保証できないものを設計で保証した好例

## 改善点

- **PR description の Test plan で `[ ]` のまま提出された**: 1st PR の時点で AC4 の手動検証 2 項目が `[ ]`（未確認）のまま提出され、reviewer がそれを fail と判定。本来は実装側（main session）が `kobaamd_implement_code` の終了条件として「AC4 が検証必須なら検証してから PR を出す」を踏むべきだった。`kobaamd_implement_code` の AC 解釈ロジックに「(手動検証推奨)` という文言が AC にあれば AC 自体が手動検証の実施を要求している」と明示する余地がある
- **PRD で AC4 を「(手動検証推奨)」と書いた曖昧さ**: 「推奨」のニュアンスが「やらなくても良い」と読まれた可能性。`kobaamd_create_prd` のプロンプトで「`(手動検証推奨)` ではなく `(手動検証必須)` と書く / ASCII 弱形修飾子は使わない」と明示すべき。本ケースは reviewer が実装側の「推奨を skip した」解釈を fail として救ったが、毎回 reviewer 任せでは不安定
- **PR 作成時に `[ ]` を残す慣行があった**: PR description Test plan の `[ ]` は「これから実施するチェックリスト」のはずが、実態は「実施しないまま merge を試みる項目」になっていた。`kobaamd_implement_code` の PR 作成プロンプトで「Test plan の全項目を `[x]` 化してから PR を出す。`[x]` 化できない項目があれば AC 自体を carve すべき」を明文化する
- **構造的整合性で済ませる範囲の設計判断が PR description に出ていない**: 「legacy ↔ subagent 跨ぎ実機テストは API key 不在で実行できないが、共通ヘルパを呼ぶ構造で整合性を保証する」という判断を rework comment ではなく **初手 PR description に書くべきだった**。reviewer は構造的保証を読み解いて評価できるが、それを PR 作成側が省略すると一発で fail に倒される
- **shell script の構造変更（380 行追加 / 183 行削除）は Codex CLI に依頼すべきだったか議論余地**: KMD-153 の learning では「< 30 行は main session 直接 Edit 可」としたが、本 PR は明らかに「構造変更を伴う規模」。CLAUDE.md の役割分担表を「shell script の小規模 surgical fix（< 30 行 / 関数追加なし）は main 直接 Edit、構造変更（共通ヘルパ抽出 / 関数分割 / 流れ変更）は Codex CLI」のように二段化する余地がある
- **Backlog 滞留 ~15h は priority Low / `Improvement` ラベル issue の典型挙動**: KMD-153 でも同種パターン（11h30m）。`pipeline_active` の 30 分間隔では十分な機会があるはずだが、`kobaamd_assign_work` の優先度ロジックが他の WIP を優先している可能性。観測継続課題

## 教訓

1. **`(手動検証推奨)` のような弱形修飾子を AC に書くと skip される**: `kobaamd_create_prd` のプロンプトで AC は二値（必須 / 不要）に倒すべき。「推奨」「望ましい」のような曖昧表現は AC ではなく「テスト戦略」セクションに移し、AC は yes/no 検証可能な形だけ残す
2. **AC が「手動検証」を要求するなら PR 作成前に実施するのが筋**: `kobaamd_implement_code` の終了判定に「PR description の Test plan が全 `[x]` 化されていること」を含める。`[ ]` が残るなら未完成であり、PR を出すべきではない
3. **`postmortem-patterns §18` が reviewer 側のゲートとして実運用入り**: KMD-153 で言語化 → KMD-155 で reviewer が引用して fail 判定 → 解消後 APPROVE、というサイクルが観測できた。wiki 投入が AI ワークフローの fail 判定根拠になっている事例として記録価値が高い
4. **構造的保証を設計に組み込むと、テストできない条件をパスできる**: legacy ↔ subagent 跨ぎは API key 不在で直接実行できないが、共通ヘルパに集約する構造で整合性を保証 → reviewer もそれを認めた。テスト不可能な互換性検証は **共通実装に集約することで構造的に保証** が標準パターン
5. **rework 指示の具体性が rework 速度を決める**: 1st review_pr が「推奨 A: 手動検証 + ログ提出」「推奨 B: bats 化」と二択を提示し、実装側は迷わず A を選択 → 22 分で完走。**reviewer が rework 指示に「具体的な実施手順 + 提出物の形式」まで書く**ことが auto-pipeline のスループットを決める
6. **shell script の構造変更（共通ヘルパ抽出・関数分割）は Codex CLI 委託の検討対象**: 380 行 / 183 行規模の refactor は明らかに「surgical fix」を超える。KMD-153 の「< 30 行は main 直接 Edit」を維持しつつ、上限を超えたら Codex に投げる線引きを CLAUDE.md に追記
7. **副次 cosmetic bug は rework 中に同 PR で解消するのが自然**: stderr の二重 prefix bug は本 PR の検証中に observable になり、3 行修正なので別 carve するほどでもない。「rework 中に発見した独立 cosmetic bug は同 PR で解消、ただし commit を分離して rationale を残す」が運用しやすい
