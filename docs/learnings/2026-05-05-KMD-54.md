## アーキテクチャ判断

### 1. lint と report を分離した

`/kobaamd_lint_wiki` 自体は KMD-52 で完成しており、本 issue の責務は「定期実行 + Linear 通知」のみ。そこで `lint.sh`（NDJSON 出力）と `lint_report.sh`（NDJSON → markdown + Linear comment.add）を **明確に分離** した。

- lint.sh は KMD-52 範囲、本 PR では一切触らない（PRD section 8「変更してはいけない箇所」に明記）
- lint_report.sh は lint.sh に **依存せず**、stdin の NDJSON だけで完結する単体スクリプト
- weekly slash は両者をパイプで繋ぐだけ

これにより lint.sh の仕様変更（KMD-52 のリファクタ等）が lint_report.sh に波及しない。後続の自動テスト整備（KMD-141）も lint_report.sh 単体で書けるようになった。

### 2. KMD-52（PR #62）未マージでも安全に動かす gate を入れた

本 PR と KMD-52 は依存関係にあるが、マージ順序が逆転しても weekly が落ちない設計を選んだ。

```bash
if [[ ! -x ./scripts/wiki/lint.sh ]]; then
  echo "wiki lint: lint.sh not found, skipping (KMD-52 not merged yet)"
else
  ...
fi
```

PR #63 は実際 PR #62 より **先にマージされた**（fd77e16 vs その直前）。この gate がなければ weekly が KMD-52 マージ前に走った瞬間に落ちる。レビュー側もこの gate を「pass」と判定しており、依存逆順耐性が機能した。

### 3. epic 解決を script 化（決め打ちを避ける）

KMD-44（[KB] kobaamd ナレッジベース整備）はエピック ID として spec 上 fix だが、IDをコードにベタ書きする代わりに `lq.sh issue.list --team KMD` で title 検索 → 見つからなければ KMD-44 にフォールバック、という二段構えにした。これは「Linear epic の identifier が将来変わる/再作成されるケース」への保険。

### 4. `--no-llm` を強制した

weekly は無人実行なので、Haiku ベースの section-context-missing 判定が失敗しても気付ける人間がいない。決定的ルール 4 観点（orphan / broken-link / stale / frontmatter）だけで劣化検知に十分という割り切り。Haiku 経由のチェックは手動実行に委ねる。

## 良かった点

1. **PRD section 8（影響範囲マップ + 変更してはいけない箇所）が機能した**: `kobaamd_review_pr` が「PRD section 8 マップ通り 3 ファイルのみ変更」「マップ外への手出しなし」を観点として独立評価できた。implement 側がマップを意識して書いていたため、レビュー側の判定が一発で通った（KMD-22 で生まれた「影響範囲マップ」プラクティスの効能が再確認できた事例）。

2. **依存逆順耐性（lint.sh 不在ガード）が PRD と実装の両方で予防的に書かれていた**: PRD section 8「その他リスク」で先に明文化され、実装と weekly slash の両方に gate が入った。レビューも同観点を pass。「依存先がマージされていないかもしれない」を前提に書く文化が定着している。

3. **shell quoting / set -euo pipefail / trap cleanup / 入力バリデーション** のパターンが implement 段階で全て入っていた: `security-hardening.md` 由来のクォート規約、`postmortem-patterns` パターン 8/9 の対称性チェックを、implement 側が **ガイドされなくても自発的に適用** している。Wiki 参照ポリシー（Prompt Caching 標準）が Wiki から実装プロンプトへ知識転移する経路として機能している証左。

4. **auto carve-out が機能した**: `review_pr` が「テスト整備（KMD-141）」「投稿失敗 observability（KMD-142）」を独立改善として認識し、本 PR を block せず別チケットに退避。**Human in Review に入らずクリーン APPROVE 直行**できたため、Reviewed → Done が約 4 分。

5. **dry-run 4 ケース（空 stdin / 不正 JSON / threshold 未満 / fixture）の証跡が PR description にそのまま貼られている**: レビュー側の検証コマンド再実行が容易で、レビュー時間を短縮できた。

6. **自動 carve-out で起票された KMD-141 / KMD-142 の本文に `親チケット: KMD-54 (auto-carved-out by kobaamd_review_pr)` と `補足: 人間が「本 PR で対応すべき」と判断した場合は本チケットを revert/close して、KMD-54 を re-open してください` が入っていた**: 人間判断のリカバリ経路が明文化されており、carve-out の取り消しが可能であることが運用上担保されている。

## 改善点

1. **AC7 の「launchd 実機検証」が PR 内では実施できず、KMD-52 マージ後の手動確認に持ち越しになった**: PR description で明示的に持ち越したのは妥当だが、現時点で誰がいつその手動確認をするかのオーナーシップが曖昧。`kobaamd_merge_pr` の post-validate hook か、KMD-44 epic 側でフォローアップ task として残すべき。

2. **Backlog → Todo に約 2 日（人間承認待ち）かかっている**: これは仕様（人間承認ゲート）どおりだが、リードタイムの大半を占める。AI 起票時の priority 4 デフォルトは `kobaamd_research_create_ticket` の挙動なので、KB2 のような「epic 配下の確定スコープ」は priority 3 で起票してよい可能性がある。ただし仕様上の「人間が承認意思を示すゲート」を緩めるかは別議論。

3. **KMD-52 が未マージのまま KMD-54 を実装した（依存逆順）**: 結果的に gate で凌げたが、原因は pipeline_active が「Todo に入った順」に処理し、依存関係を見ないため。`kobaamd_assign_work` に「parent の状態 / blocked-by ラベル」を見て依存解決を待つ機能があれば、依存逆順耐性のためのガードコードを書く必要が減る。

4. **carve-out 先（KMD-141 / KMD-142）が backlog に積まれただけで、TTL や定期再評価の仕組みがない**: 「auto-carved-out が放置されないか」を可視化する仕組み（detect_stale 系で「auto-carve label つきで N 週放置」を通知する）があると、carve-out の信頼性が上がる。

5. **`lint_report.sh` の comment.add 失敗時は `err "failed to post Linear comment"` を stderr に出して exit=0 で抜ける** という設計（weekly 全体を落とさない）に対し、observability の不在が KMD-142 として carve-out された。これは設計判断としては正しいが、PRD 段階で observability を最低限担保する（`.logs/lint_post_failures.jsonl` への追記など）案を検討してから割り切る方が望ましかった。

6. **PRD 内の「issue 本文では `com.kobaamd.weekly.plist` と書かれているが実体は `com.kobaamd.pipeline_weekly.plist`」という表記揺れ修正は、本 PR では plist を触らないとの判断**: 妥当だが、issue description 自体の表記揺れは残ったまま。`kobaamd_research_create_ticket` のプロンプトに「launchd plist 名は実体と一致させる（ヒアリング: bundle 名と plist 名が異なる場合は両方併記）」を追加すべき。

## 教訓

- **PRD section 8（影響範囲マップ + 変更してはいけない箇所）は防御的に書くほどレビューが速くなる**: 「触らないファイル」を列挙するだけで review_pr の観点判定が「マップ外への手出しなし」を独立評価できる構造になる。implement 側もマップに従う動機が強くなる（後で review_pr に指摘される）。
- **依存先未マージ前提のガードを PRD で明文化する**: 「依存元 PR が先にマージされる可能性」を PRD section 8「その他リスク」に書くと、implement と review の両方が gate を確認する観点として機能する。本件の lint.sh 不在ガードが好例。
- **責務分離（lint.sh / lint_report.sh）は単体テスト容易性に効く**: 後続の auto carve-out（KMD-141）が「lint_report.sh 単体で fixture-driven test を書く」として成立する。逆に lint.sh と report が一体だと、lint.sh の差分でテストが壊れやすい。
- **クリーン APPROVE 直行の条件**: (a) PRD AC が網羅的、(b) 影響範囲マップ通りの変更、(c) wiki-derived patterns（quoting / set -euo pipefail / trap / バリデーション）を implement 側が自発適用、(d) auto-carveable concern は別チケット化、の 4 点が揃うとリワーク 0 で Reviewed 直行できる。本件はこの 4 点が全て揃った理想ケース。
- **`--no-llm` のような「無人実行モードの明示フラグ」は weekly / daily ジョブで有効**: 無人実行で stderr を読む人間がいない前提を割り切って受け入れる。確率的失敗を許容する LLM 経路を deterministic 経路に切り替える設計判断は、運用負荷を大きく下げる。
- **Auto carve-out には re-open 手順をコメントに明記する**: 「人間が本 PR で対応すべきと判断した場合は KMD-141/142 を close/revert して KMD-54 を re-open」と書いておくと、carve-out の妥当性に疑問を持った人間が取り消し可能。これがないと carve-out が「AI による責務逃れ」に見えてしまう。
