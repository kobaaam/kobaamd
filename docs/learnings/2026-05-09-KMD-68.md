# Postmortem: KMD-68

## サマリ

KB3（KMD-56〜62）が未着手のまま、kobaamd エディタの全文検索を SQLite FTS5 + BM25 ベースに置き換える先行実装案件。`WikiIndexService.swift`（368 行）を新規追加し、`SearchViewModel` を indexed/grep フォールバック構造に変更。1 回目 review_pr で **F1: snippet `<<...>>` マーカー剥き出し / F2: lineNumber=1 固定の虚偽情報** の 2 件が REQUEST_CHANGES、`kobaamd_fix_pr_comments` 1 周で `replacingOccurrences` 適用 + `lineNumber: Int?` Optional 化により surgical 修正、再 review でクリーン APPROVE → Reviewed 直行 → 自動マージ。リワーク 1 周で完走したが、**いずれの fail も「FTS5 の内部表現を ViewModel/Presentation 層で吸収する責務」が PRD §5 と review_prd で見落とされた点**が共通根本原因。auto-carveable concern 8 件 + human-judgment 1 件を残したが、ユーザー指示で全て auto-carve 扱いに統一。security review は WARNING（CRITICAL なし）で、`.env` 等の機微ファイルが平文で `.kobaamd/index.sqlite` に永続化される副作用が新リスクとして浮上。

## 良かった点

- **`fix_pr_comments` 1 周で APPROVE 直行できた**: F1/F2 が ViewModel 層に閉じる surgical fix（snippet マーカー除去 + `Int?` Optional 化）で、Codex Sonnet 4.6 が想定通りに修正。`SearchViewModel.swift` の数行 + `SearchView.swift` の `if let lineNumber` ガードのみで Service 層 (`WikiIndexService`) や SQL クエリ側 (`snippet()`) を一切触らずに済んだ。**MVVM 階層を保った修正設計**が再 review のクリーン APPROVE を引き出した
- **既存 `SearchViewModelTests.lineNumberIsCorrect` が Optional 化後も Swift の `Int?? == Int` 比較で素通り**: `vm.results.first?.lineNumber == 3` がそのままパスし、テスト追加なしで回帰検出可能だった点は Swift 言語仕様の幸運だが、PR description で明示的に「test ターゲット build 成功で確認」と書いた reviewer の確認は丁寧
- **review_pr の `SearchView` 整合確認**: PRD §8 の影響範囲マップに `SearchView.swift` が未記載だったが、reviewer が「『SearchView の UI 既存 grep 互換結果表示を維持』とは抵触しない」と能動的に判定し、auto-carveable C8 として記録した上で本 PR をブロックしなかった。**マップ漏れを auto-carve として処理する判断ロジックが再現できる形で記録された**
- **review_security が WARNING で機微情報リスクを正しく検出**: `.env` ファイルが `.kobaamd/index.sqlite` に平文永続化される副作用を新リスクとして検出し、CRITICAL なしと判定して本 PR はブロックせず、carve-out 推奨として明示。「grep は実行時メモリだけだが SQLite DB は vault root にディスク常駐し、誰かが DB ファイルだけ持ち出した場合に漏えいする」という**新リスクの定式化**が観点として残った
- **Gemini UI/UX 検証が 1 回目で F1/F2/C1/H1 の 4 点を機械的に列挙**: `<<...>>` マーカー / `L1` 固定 / building インジケータ欠落 / phrase 一致挙動差を Gemini 側でも独立に検出。`kobaamd_review_pr` と Gemini 両方の判定が一致する diff は信頼性が高い
- **依存先 KB3 (KMD-58) 未着手下での先行実装方針を PRD §1/§8 で明記**: 「KB3 の `scripts/wiki/ingest.sh` 未着手のため Swift 側で読み書き両方実装、後続 KMD-58 が同じスキーマを採用する想定。KMD-58 着手時に再評価」と PRD で透明に開示。フェーズ間の依存逆順（依存元が依存先より先にマージ）を意識した運用が `dependency-inversion-guard` パターンと整合
- **`unsafeBitCast(-1, to: sqlite3_destructor_type.self)` の `SQLITE_TRANSIENT` 表現を review_security が「SQLite 公式ドキュメントでも紹介されている標準イディオム」と認定**: Swift から C マクロを表現する慣用句を機械的に「危険な API 使用」と分類せず、文脈で安全と判定した点は wiki-derived の良い適用例

## 改善点

- **F1（snippet マーカー剥き出し）/ F2（lineNumber=1 固定）が PRD と review_prd の両方で見落とされた**: PRD §5「matchLine（grep 互換）を表示」と AC「該当行付き」は仕様レベルで FTS5 の生 snippet 出力をそのまま貼り付けることを禁止しているはずだが、PRD は「既存 SearchView を維持。検索結果に matchLine（grep 互換）を表示」という抽象表現にとどまり、**FTS5 の `snippet()` が `<<keyword>>` を返す事実 / FTS5 では行番号が取得できない事実**を PRD に書き起こさなかった。implement_code は仕様の抽象表現を素直に「snippet をそのまま代入」として実装し、review_prd（あれば）でも見落としやすい位置にあった。実装直後の段階で「データ表現が grep の matchLine と互換でない」点が透明に開示されないと AC のテストが書きづらい
- **`SearchResult.lineNumber: Int` から `Int?` への構造変更を実装段階で見落とした**: `lineNumber: 1` を全件固定代入したのは「`SearchResult` の API シェイプを変えたくない」という遠慮の結果と推測。仕様（行番号が取得できない）に合わせて型を変える判断が implement_code 時点では取られず、review/fix_pr_comments で型変更を後追いした。**「データ表現が仕様と矛盾する場合、API シェイプを変える勇気を持つ」**が implement プロンプトに足りていない
- **PRD §3 必須要件「`workspaceRootChanged` 通知に Swift 側でバックグラウンドインデックス化を起動」が `refreshQuickOpenIndex` ピギーバックに置き換わった**（C6 として auto-carve）: 動作はするが PRD と乖離。implement_code は「既存通知購読箇所がなければ最小エントリポイント追加」という PRD §8 の文言を緩く解釈し、ピギーバックに倒した。PRD §3 の通知購読要件を満たすかは review 観点でも初回見落とされ、re-review 後 carve に逃げた形
- **PRD §8 影響範囲マップが `SearchView.swift` を欠いていた**（C8 として auto-carve）: 実装は `SearchView` の `.onAppear` に 4 行追加（`AppViewModel.searchIndexService` 注入）したが、PRD のマップは Service / SearchViewModel / AppViewModel の 3 ファイル。マップ更新が implement_code 段階で漏れた。`postmortem-patterns §1 影響範囲マップ必須化` は遵守したが、**実装後にマップを diff 反映する後処理ステップが欠けている**
- **`private nonisolated static func` の SourceKit 警告 vs swift build pass の乖離が PR description に明記された運用は良いが、wiki 化されていない**: PR description / Linear コメントに「swift build (Apple Swift 6.0+) でも警告は出ず、SourceKit の診断ノイズのみ」と書いて reviewer 側を案内したのは丁寧だが、これは IDE / CLI ツール gap の典型ケースで、再発時に同じ説明を毎回書くコストが残る
- **DB スキーマを KB3 (KMD-58) と未調整のまま先行確定した点は許容範囲だが、後続レビューポイントが残った**: PRD §8 で透明に開示しているのは良いが、**KMD-58 着手時に「再評価」をどう機械的に発火させるか**（KMD-58 の PRD §10 関連資料に KMD-68 を必ず明記する運用ルール / レビュー時に DB スキーマ整合性を独立観点として確認する観点追加 等）が無いと忘れられる
- **security review WARNING の `.env` 副作用が auto-carve 起票されないまま postmortem に流れた**: review_security コメントは「別 issue として carve-out を推奨」と書いたが、`/kobaamd_carve_concerns KMD-68` は本サイクルで起動されておらず、**security WARNING が機械的に carve-out チケット化される経路が欠けている**。手動カーブに依存している
- **Backlog 滞留 ~6 日**: 2026-05-03 起票 → 2026-05-09 着手。kb-pipeline ラベル + priority 4 (Low) のため pipeline_active が拾わず、人間承認（priority 上げ or label 外し）待ち。承認ゲート設計上の意図的な滞留だが、KB pipeline 全体の進捗観測には `kobaamd_detect_stale` の閾値を kb-pipeline ラベル付きには別設定する設計余地がある

## 教訓

1. **PRD では「内部表現が UI に剥き出し露出する箇所」を明示的に列挙する**: FTS5 `snippet()` の `<<...>>` のような「ライブラリが返す内部マーカー」が UI 層に到達するパスは ViewModel で吸収する責務である、と PRD §5 で明文化する。`<<keyword>>` のように具体例を 1 つ書くだけで implement_code が見落とさなくなる。`prd-quality-cycle` 拡張候補
2. **データ表現が仕様と矛盾する場合は API シェイプ（型）を変える**: `lineNumber: Int` を `Int?` に変える判断が implement 時点で取れていれば、F2 の rework は防げた。「仕様に合わせて型を変える勇気」を `kobaamd_implement_code` Constraints に明記する。`postmortem-patterns` 新パターン候補
3. **fix_pr_comments 1 周で APPROVE 直行できる surgical fix の条件**: ViewModel/Presentation 層に閉じること / Service・SQL 層を触らないこと / 既存テストが Optional 比較等で素通りすること。本ケースは 3 条件揃って 5 分で完了。`postmortem-patterns §7 クリーン APPROVE 直行 4 条件` の **fix 後直行版** として追加価値あり
4. **影響範囲マップは「実装後 diff 反映」の後処理ステップが必要**: implement_code が PR を作る前に PRD §8 マップを diff（実際に触ったファイル）と照合し、漏れがあれば PRD に追記する。マップ漏れが auto-carve（C8）に流れる現運用は許容できるが、PRD 鮮度が下がる
5. **依存先未着手で先行実装する場合は「後続再評価のフック」を機械的に設置する**: KB4 (KMD-68) が KB3 (KMD-58) のスキーマ未確定下で先行確定した DB スキーマは、KMD-58 着手時に再評価が必要。KMD-58 PRD の §10 関連資料に KMD-68 を必須リンクとして埋める / KMD-58 PRD AC に「KMD-68 で先行確定したスキーマと整合性を取る」を必須化する。`kobaamd_create_prd` のプロンプトに「依存先 issue の PRD §10 から本 issue を参照されているか確認」観点を追加候補
6. **vault root に永続化される SQLite DB は機微ファイル拡張子レベルで除外する**: `.env` / `*.key` / `credentials*` 等を `WikiIndexService` の専用除外リストで弾く設計が必要。`FileService.supportedExtensions` から `env` を外すと grep 側にも影響するため、**WikiIndexService 専用の除外リスト**を持たせる責務分離が筋。security carve-out チケット起票が必須
7. **security review WARNING を機械的に carve-out 起票する経路が必要**: 「別 issue として carve-out を推奨」というコメントが手動起動 (`/kobaamd_carve_concerns`) 待ちで stuck する運用は脆い。`kobaamd_review_security` が WARNING を検出した時点で auto-carve（priority Low / `security` ラベル付き）まで一気通貫させる、または review_security の最終ステップで `kobaamd_carve_concerns` を自動起動する経路を検討
8. **SourceKit 診断ノイズ vs swift build pass の乖離は wiki 化が望ましい**: `private nonisolated static func` 修飾子順序のような IDE/CLI gap は再発する性質の問題で、PR description で都度説明するより wiki 記事として固定化したほうがコスト低い。`practices/swift-toolchain-quirks.md` (新規) または `architecture/editor-core.md` への追記候補
