## 良かった点

- **review_pr の批判観点が機能した（mock hash 不一致の検出）**: 初回レビューで「mock claude が返す固定 hash `abc123` は本物の `shasum -a 256` と不一致 → emit_if_violation の出力が `{\"line\":null,...}` になり、`jq -e .` は null を valid とみなすため誤 PASS していた」という形骸化テストの問題を正確に指摘。review_pr の「テスト assertion が実装意図を正しく検証しているか」という批判角度が有効に働いた
- **fix_pr_comments が 2 件の指摘を 1 コミットで一括修正**: hash 動的計算への書き換え・`.line | type == \"number\"` assertion 追加・workflow パスケース統一を 1 コミット（723f1ea）で完了。rework 後の第 2 回レビューでクリーン APPROVE を得た
- **review_security が CI パス不一致を機能バグとして独立指摘**: security reviewer が「Tests/wiki（大文字）vs tests/wiki（小文字）の不一致は Linux CI では ENOENT」を機能観点で副次的に発見。functional reviewer にも引き継ぎする形で記述しており、dual-review 体制が相乗効果を発揮
- **validate_build が smoke test 9/9 PASS を確認**: 初回コミット時点（形骸化状態）でも `run_subagent()` の基本動作は確認できた。形骸化の検出は validator ではなく reviewer の役割であることが明確になった
- **auto-carve 連鎖の観察**: KMD-153 の review_pr が smoke test を KMD-171 として carve → 本チケットが単独で完結する「親 PR をブロックしない carve-out 設計」が 2 段機能した（KMD-150 → KMD-153 → KMD-171）

## 改善点

- **mock のデータは本物の処理と同じ計算で生成すべきという原則が PRD/実装プロンプトに未記載**: Codex CLI が mock に固定値 `abc123` を使ったのは自然な選択（unit test では sentinel 値を使いがちな慣習）だが、本件では section-context-check.sh が shasum -a 256 を内部で計算して参照するため、sentinel 値を渡すと実際の処理経路を経由しない形骸化テストになる。実装プロンプトに「mock の入力値・ハッシュ値は本物の処理と同じ方法で計算すること」を明記する必要があった
- **macOS case-insensitive FS がローカル動作確認を通過させてしまった**: 開発機（macOS）では `Tests/wiki` と `tests/wiki` が同一パスになるため、Codex CLI が小文字 `tests/wiki/` で workflow を書いてもローカルで動作する。CI（ubuntu-latest）で初めて ENOENT が顕在化する。review_security に副次的に指摘されなければ CI は全く動かない状態でマージされるところだった。`kobaamd_validate_build` のローカル smoke test も `Tests/wiki/` を直接実行するため、パスケースの不一致を検出できなかった
- **Backlog 滞留 164 時間**: priority Low / Improvement ラベルの auto-carve issue は他の TODO issue（通常 priority）に押し負ける運用になっている。KMD-153 の postmortem でも同傾向が記録されており、auto-carve issue の滞留傾向が構造的問題として蓄積されている
- **`kobaamd_validate_build` のチェック範囲が CI 挙動をカバーしていない**: workflow の paths filter が正しく動くか・runner の FS 挙動と一致するかは `validate_build` では確認できない。「CI では動くが CI 未起動 / CI に届かない」という種の不整合を検出する仕組みがない

## 教訓

1. **mock のデータは本物の処理と同じ計算で生成すべき**: テスト対象が内部で計算した値（hash / timestamp / UUID 等）を参照する場合、mock 側に sentinel 値（固定文字列）を渡すと実際の処理経路を外れた形骸化テストになる。実装プロンプトに「mock 値は本物の計算ロジックを経由して生成すること / sentinel 値を使う場合は処理経路をバイパスしていないか明示的に確認すること」を追加する
2. **macOS case-insensitive FS は Linux CI の罠を隠す**: workflow / Makefile / スクリプトのパス文字列は大文字・小文字を実 FS と一致させなければ、開発機では通り CI で ENOENT になる。`kobaamd_implement_code` プロンプトに「ファイルパスを含む workflow や Makefile の変更では、macOS 開発機と Linux CI runner の FS case-sensitivity の差を意識すること。`ls <path>` で実際のケースを確認してから文字列に使うこと」を追記する
3. **review_pr は「テスト assertion が実際の処理経路を通っているか」という批判観点を持つべき**: `jq -e .` のような緩い assertion は null / 空 JSON でも PASS する。review_pr のプロンプトに「smoke test / unit test の assertion が、テスト対象の実際の処理経路を外れた形骸化テストになっていないか確認する（特に mock 戻り値と本物の計算結果の一致を疑う）」を追加する
4. **auto-carve 連鎖の 3 段目（孫チケット）は priority Low 滞留が深刻になる**: KMD-150 → KMD-153 → KMD-171 と 3 段 carve が起きたとき、孫チケットの Backlog 滞留は 164 時間に達した。自律パイプラインのスループット観点で「n 段目以降の auto-carve issue には priority 自動昇格ロジックを入れる」または「2 段 carve は原則禁止（孫まで carve する場合は人間に確認する）」の方針を検討する
