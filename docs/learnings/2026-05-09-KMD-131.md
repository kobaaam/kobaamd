## 改善点

- **当初実装が誤った前提（「subagent 冒頭で 1 回」）を疑わずに進めた**: Claude Code の Bash tool 挙動を確認せずに、PRD のゴール文「subagent 冒頭で 1 回に集約」をそのまま実装に落とし込んだ。実際には subagent / pipeline は通常複数の Bash invocation を実行するため、`source` 効果は invocation をまたいで持続しないという基本事実が抜けていた。**「Claude Code の Bash tool が invocation ごとに subshell 独立か、それとも親シェルを継承するか」を確認するステップが PRD / 実装どちらの段階にも組み込まれていなかった**
- **PR タイトルに旧（誤）表現が残ったまま merge された**: 「subagent 冒頭で 1 回に集約」というタイトルは本文中で否定された旧表現を文字通りには含む。本文・PRD・コードコメント側では正しい新表現に再定義されているが、squash merge 後の commit message にも旧表現が残り、`git log` を後から眺める人にとって誤解の温床になり得る。本 PR では修正コストの観点で許容したが、リワーク後にタイトル更新を行うべきだった
- **PRD のゴール文が誤った前提を内包していた**: PRD のタイトル「subagent 冒頭で 1 回に集約」と section 3「subagent あたり 1 回 source される」は、`kobaamd_review_prd` 段階では誰も指摘していない（Bash tool 挙動を実機検証する PRD レビュー観点が無い）。**PRD 段階で「環境変数スコープに関する想定があるか」「Claude Code の Bash tool 挙動と矛盾しないか」をチェックするゲートが欠けている**
- **自己 PR 制約により `gh pr review --request-changes` が使えず、`needs-fix` ラベル代替経路を踏んだ**: これは GitHub 仕様起因の既知制約で運用は機能しているが、`fix_pr_comments` の引きをラベルベースで設計している点を新規 contributor が理解しにくい。CLAUDE.md / wiki に明文化されていれば運用上の認知負荷が下がる
- **Backlog 滞留 ~2.5 日**: 2026-05-05 起票後、人間承認ゲート（priority 引き上げ or label 外し）待ちで滞留。これは設計どおりではあるが、auto-carve 起票（priority 4 / `pipeline-resilience` ラベル）issue の承認スループットが運用ボトルネックになっている可能性。同時期の他 issue にも同傾向があるなら `kobaamd_detect_stale` で観察したい

## 教訓

1. **Claude Code の Bash tool は invocation ごとに独立 subshell**: これは「環境変数を引き継ぎたければ各 invocation の冒頭で `source` する」「同一 Bash call 内なら heredoc / 後続コマンドに env が引き継がれる」という運用に直結する。subagent / slash command を新規追加するときの普遍的前提として明文化すべき。本記事を書いた最大の動機
2. **「環境変数スコープ」は PRD レビュー観点に明文化されていない死角**: 「subagent 冒頭で 1 回」という表現が PRD と実装の両方を素通りした事実は、`kobaamd_review_prd` / `kobaamd_create_prd` のチェックリストに「環境変数 / シェル状態に関する仮定が Claude Code の挙動と整合するか」を加える必要を示唆する
3. **review_pr の「実機検証」は文言レビューでも有効**: 「subagent 冒頭で 1 回」のような自然言語の前提は、grep / lint だけでは検出できない。実際にコマンドを 2 回叩いて「invocation 間で env が消える」のを確認するパターンは、文言系 PR でも汎用的に再現できる
4. **shell script 変更ゼロ・ドキュメント変更のみの PR は、main session 直接 Edit が最適解**: KMD-153 の learnings で議論された運用と同じく、Codex 経由の往復コストを払わず、CLAUDE.md の役割分担ルール（Swift ファイル限定）にも抵触しない。CLAUDE.md / `role-dispatch.md` に「ドキュメントのみの変更も main session 直接 Edit 可」を明記する余地
5. **PR タイトル / commit message は旧表現が残ると後の検索体験を毒する**: 本文や PRD で再定義しても、`git log` / GitHub の PR 一覧 / Linear タイトルに残った旧表現が、未来の grep / 検索を誤誘導する。リワークで前提が反転した場合、**タイトルも併せて更新するのを review_pr の concern に含める**運用が望ましい
6. **auto-carveable 2 件をリワーク同 PR で吸収する判断は spec の安定性に貢献**: auto-carve 起票のオーバーヘッド（issue 起票 + 別 PR + 別 review サイクル）を回避し、PR の self-contained 性を上げる選択は、リワーク中に余裕があれば積極的に取ってよい
7. **Backlog 起票から Done まで 3.22 日のうち、AI が能動的に動いていたのは ~24 分**: 残りは人間承認ゲート待ち。能動フェーズだけ見れば極めて高速で、KMD-153（23 分）に続いて「小規模ドキュメント PR は 30 分以内」のベンチマークが累積しつつある
