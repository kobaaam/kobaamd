# Postmortem: KMD-133

## サマリ

`kobaamd_review_postmortem` 完了後の `kobaamd_update_wiki` 連鎖を `wiki_value: high|medium|low` フィールドで gate し、低価値 learnings の取り込みコスト（〜5k tokens / 件）を削減する infra 改善 PR。実装は .md 4 ファイル / +76/-13 行の小規模だが、自分自身が「postmortem の wiki 価値判定」を導入する PR 上で **postmortem-patterns §16「subagent MD 編集時の frontmatter 整合チェック」が再発した**という極めて示唆的な事例となった。§16 は KMD-120 (5/8 03:18 UTC) で auto-carve（KMD-156）された約 16 時間後の同じ日 (5/8 19:24 UTC) に同じ panttern が再発しており、**wiki に対策が文書化されていてもプロンプト本体に反映されないまま再発する**という新メタパターンを明示した。

## 良かった点

- **review_pr の wiki-derived patterns 観点が機能した**: 1 周目 review_pr が「postmortem-patterns §16『subagent MD 編集時の frontmatter 整合チェック』に直接該当」と明示参照して fail 判定を下した。.md only PR でも wiki-derived patterns ゲートが具体的な根拠付きで動作することを示した参照実例（.md only は UI/UX 観点が N/A になり Gemini 検証も skip されるため、wiki-derived patterns が事実上の主観点になる）。
- **review_security と review_pr の並行で 1 サイクル終結**: review_security が同 1 周目で「INFO: `${LAST_MONTH}` 非クォート」を検出 → fix_pr_comments が同じ修正サイクルで両方ついで対応 → 2 周目 review_pr が両方の解消を確認して APPROVE 直行。INFO レベルの security concern を独立 issue 化せず、進行中の rework サイクルに合流させたのが効率的だった。
- **review_security のゲート観点絞り込みが適切に機能**: postmortem-patterns §19「review_security はゲート観点を PR の本質に応じて選ぶ」が実装されており、本 PR は「postmortem 連鎖の gate ロジック追加」=「観測機構の新設ではない」と判定して §12 の重い AC（`set -u` + `trap` + `local` 互換性検証等）を適用範囲外として除外した。レビューコメントに「パターン 19 に従い、PR 本質に応じたゲート観点（shell snippet の入力経路 / クォート規約）に絞ってレビューした」と明示記録があり、観点リストを上から舐めない判断ロジックが運用中。
- **3 件の auto-carveable concern を 2 周目で持ち越さず Reviewed 直行**: 1 周目で auto-carve 候補 3 件（pipeline_weekly の `5b.` 非標準 ordered list / log.md sources 突合 shell snippet 不在 / launchd `StartCalendarInterval` の catch up 不在）を明示し、2 周目は「ユーザー指示通り、再評価でも判定変えず本 PR をブロックしないため Reviewed 直行」と一貫処理した。concern 三分類（rework / auto-carveable / human-judgment）の判定が周回をまたいで安定している。
- **AC 4 項目が機械的にチェック可能な形で書かれていた**: PR body の「AC 充足確認」セクションで PRD AC 1〜4 が個別チェックボックスでマップされ、review_pr が PRD AC との整合 pass を即座に確定できた。

## 改善点

- **postmortem-patterns §16 が「文書化済み・実装未反映」の状態で再発した**: §16 は KMD-120 で auto-carve（KMD-156）され、`docs/wiki/articles/practices/postmortem-patterns.md` および `subagent-prompt-design.md` §4 にも明文化されている。さらに KMD-120 の learnings (5/8 作成) のアクション #54「`kobaamd_implement_code` の Constraints / Workflow に subagent MD 編集時の frontmatter 整合チェックを追記」も書かれていた。**にもかかわらず、KMD-156 は Backlog に起票されたまま未着手で、約 16 時間後の KMD-133 で同パターンが再発**した。wiki 文書化と learnings アクションだけでは再発防止にならない。
- **`kobaamd_improve_prompt` の提案が実装パスに繋がっていない**: `kobaamd_improve_prompt` は週次（pipeline_weekly）で learnings を mining してプロンプト改善提案を出すが、生成された提案を実装に変換する subagent / slash が無い。提案は Linear コメントや Final Report に残るだけで、`kobaamd_implement_code` が拾うキューが整備されていない。**learnings → wiki 文書化（update_wiki）→ プロンプト本体への反映** までを通すパイプが切れている。
- **subagent MD の lint が無い**: `.claude/agents/*.md` の frontmatter `description:` と本文（特に `## Input modes` のようなモード一覧セクション）の整合を検証する自動チェックが無い。CI / pre-commit / `kobaamd_lint_wiki` のいずれにも該当ルールが入っていないため、目視レビューに依存する状態が続いている。`docs/wiki/SCHEMA.md` には lint 規約があるが、`.claude/agents/*.md` 用の SCHEMA は未整備。
- **KMD-156 の追跡漏れ**: KMD-156 は Backlog に置かれたまま約 1 日未着手だった。priority 4 / size XS（1 行修正）にもかかわらず `kobaamd_assign_work` の選定経路に乗らず、関連親 issue（KMD-120）が Done に移った時点で「親が完了したから子も忘れてよい」のような暗黙ルールはないはずだが、実態として優先度 4 の auto-carve 子チケットが滞留しやすい。`kobaamd_detect_stale` は N 日基準のみで「親が done になった子の auto-carve issue」を検知しない。
- **wiki_value 判定基準を `kobaamd_review_postmortem` に追加した側のメタ判定基準（自己 dogfooding）が PRD に書かれていなかった**: 本 PR は `wiki_value` gate を導入する PR だが、PRD AC には「KMD-133 自身の postmortem では wiki_value をどう判定すべきか」のメタガイダンスが無い。今回は「frontmatter 整合再発という新パターンを発見した」ため自然に high と判定したが、もし re-shipping value のない単純機能追加だったらメタ判定が曖昧になり得た。新フィールド導入時はその dogfood 適用例を PRD に書き残す運用が望ましい。

## 教訓

- **wiki に対策が書かれているだけでは再発しない保証にはならない（KMD-120→KMD-133 の 16 時間再発が証明）**: postmortem → learnings → update_wiki の連鎖が回っても、`kobaamd_implement_code` 等のプロンプト本体に反映されない限り、次の subagent 起動時に同じ取りこぼしが起こる。**wiki 化された対策で「プロンプト改修を伴うもの」は、wiki 化と同じタイミングで対応 KMD issue を Backlog ではなく Todo に直入れし、`pipeline_active` の通常実装ループで処理する**運用に倒す必要がある。
- **`kobaamd_improve_prompt` の出力を実装に流すパイプを設計する**: 現状は週次で提案テキストを出すだけ。提案ごとに「対象 subagent / 修正内容 / 影響範囲」が構造化されていれば、自動で `kobaamd_create_prd` → `kobaamd_implement_code` に流せる。**改善提案 → PRD 化 → 実装** までを 1 連の pipeline に組み込まない限り、提案は腐っていく。
- **`.md only` PR でも wiki-derived patterns ゲートが主観点として有効**: UI/UX 観点が N/A になり security 観点も軽量で済むため、レビューの実質判定は wiki-derived patterns（過去 learnings から抽出された反復パターン）に集約される。`kobaamd_review_pr` が wiki ロード（`scripts/wiki/ask.sh` ベース）で過去パターンを参照できる前提が揃っているため、.md only PR ほど review_pr の価値が顕在化する。今後 .md / .yml / .json 等の構成ファイル PR の review 戦略は wiki-derived patterns を主軸にする方針で OK。
- **INFO レベルの security concern は進行中の rework サイクルに合流させる**: 独立 issue 化せず、`kobaamd_fix_pr_comments` が rework 修正と同サイクルで対応する方が往復コストが小さい。WARN / CRITICAL は別チケット必須だが、INFO は親 PR にバンドルが効率的。`kobaamd_review_security` のレビューコメントテンプレに「INFO は同サイクル合流推奨、WARN/CRITICAL は別 issue 化」と明示する余地がある。
- **dogfooding を PRD AC に組み込む**: メタ機能（postmortem の wiki_value gate / lint ルールの追加 / プロンプト改善ガイドライン等）を導入する PR は、その機能を「自分自身に適用した結果」を PRD AC に明記する。本 PR は結果として自然に dogfood できたが、もし忘れていたら「KMD-133 自身の postmortem の wiki_value 判定が `low` で update_wiki が起動しない」など意図と異なる挙動になり得た。
- **auto-carve 子チケットの滞留検知を追加する**: 親 issue が Done になった瞬間、auto-carve された子チケットの優先度を一段引き上げるか、`kobaamd_detect_stale` の検知ルールに「auto-carved-out by ... の子チケットが N 日以上 Backlog 滞留」を追加する。現状は親完了で関心が薄れ、`pipeline-resilience` ラベルの子も含めて滞留しやすい。
