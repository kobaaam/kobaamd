# Postmortem: KMD-119

## サマリ

`launchd` 30 分起動の `pipeline_active` が 1 日 48 回中 ~38 回 no-op で終わり、毎回 CLAUDE.md (~8k tokens) と subagent プロンプトを空費していた。`.claude/commands/kobaamd_pipeline_active.md` のステップ 0b 直後に **「ステップ 0b': No-op early return ガード」（38 行）** を追加し、6 条件 (Reviewed=0 / Human in Review=0 / in Review=0 / CONFLICTING PR=0 / draft=0 / (In Progress>=1 OR Todo=0)) すべて成立時は subagent を起動せず即終了する仕組みを導入。推定 **~770k tokens / 日** を削減する。

実装初版で 2 件の rework が発生したが、`fix_pr_comments` ループで一発修正・再レビューでクリーン APPROVE に至り、自己 PR の `needs-fix` ラベル代替経路も期待通り機能した。

## 良かった点

- **`needs-fix` ラベル経路が想定通り機能**: 自己 PR では GitHub 仕様で `--request-changes` が使えないが、`review_pr` が `needs-fix` ラベルで代替し、`fix_pr_comments --auto` ループが正しく拾って In Progress に戻した。仕様書通りの挙動を本番で検証できた
- **review_pr の指摘が具体的かつ実機検証付き**: fail 1（`--json` 未対応）について「実機確認済み: `lq.sh: issue.list: unknown flag: --json`」と stderr メッセージを引用し、修正手順（フラグ削除のみで動作）まで提示。fix_pr_comments が一発で潰せた
- **review_security との並行実行**: SECURITY APPROVED が独立に投稿され、設計レビューと安全性レビューが分離。pipeline_active の並行実行設計が機能している
- **AC の数値ゴール明示**: 「no-op cycle 1 回あたり ~3k〜5k tokens 以下」「~770k tokens / 日 削減」が PRD に明記され、実装後の効果測定が判定可能
- **rework→再APPROVE まで 5 分**: AI 自律サイクルが分単位で回り、人間承認ゲート（18.5h）以外はほぼ瞬時

## 改善点

- **存在しないフラグへの依存（致命）**: 実装時に `lq.sh issue.list --json` を判定スクリプト例として書いたが、`cmd_issue_list` は `--team / --state / --limit` しか受け付けない。`set -e` 環境下では全カウント変数が空文字列になりガードがほぼ常に不成立に倒れる。**実装前に `scripts/linear/lq.sh help` または source を確認するクセが implementer / fix_pr_comments のプロンプトに不足**
- **early return の対称性欠如（observability 損失）**: 「ステップ 0c 以降をすべてスキップ」と書いてしまい、ステップ 12（post-run snapshot）まで skip される解釈になっていた。pre/post-run スナップショットのペア整合が崩れ、`.logs/pipeline_transitions.log` に no-op cycle が記録されない＝ AC の「24h 運用後 token 消費確認」自体が困難になる。**「節約系最適化を入れる時は監査ログ・スナップショット系を必ず残す」原則が明文化されていない**
- **review_pr が指摘したのに implementer が見落とした**: 実機テストなしの判定コードが PR に乗った。implementer が「lq.sh で各ステータスの件数を 1 回でも実行して動作確認する」一手間を踏めば事前検出できた

## 教訓

- **シェル / CLI ヘルパーを使う subagent は、引数を書く前に help / `--help` / source を必ず参照する**。lq.sh / gh CLI / jq の組み合わせは未対応フラグが silent に詰まる経路（`die` で stderr のみ）を持つため、目視レビューでは見逃されやすい
- **「節約系の最適化」と「観測性」はトレードオフではなく両立すべき**。早期 return / skip / no-op 化を入れる時は、監査ログ・スナップショット・ペア整合（pre/post）系のステップは **必ず残す** ことを設計原則化する
- **自己 PR の制約は仕組みで吸収できる**。`needs-fix` ラベル経路は「制約に対する代替設計が運用ループに組み込まれていれば、機械的サイクルが止まらない」良い実例
- **AC に数値ゴールを書くと事後検証が回る**。「~770k tokens / 日 削減」「~3k〜5k tokens / cycle 以下」のような測定可能な数値があると、postmortem / improve_prompt が次サイクルで効果検証できる
