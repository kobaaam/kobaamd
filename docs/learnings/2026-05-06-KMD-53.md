## アーキテクチャ判断

### 1. Codex CLI を使わず Edit ツールで直接編集した判断

CLAUDE.md「厳守ルール：役割分担」では「`.swift` ファイルを新規作成・編集するなら → Codex CLI に依頼」と規定されている。本 PR は `docs/wiki/articles/**/*.md` のみの編集で、Swift コード・Package.swift・scripts はゼロ変更。markdown は

- 文字列置換主体で創造的判断が少ない（slug 置換 / Related セクション追記）
- lint.sh の violation 出力が修正対象を機械的に特定済み
- Codex 呼び出しのオーバーヘッド（プロンプト準備 / 結果取り込み / レビュー）が編集時間より長い

という性質のため、**Codex を経由せず直接 Edit するのは規約違反ではなく合理判断**だった。CLAUDE.md の対象は「Swift / SwiftUI 実装」であり、wiki ドキュメントの規約適合は対象外と読める。ただしこの解釈は明示されていないため、暗黙のうちに「.md / docs だけの編集は Edit 直接編集 OK」がエージェント間で共有されていた可能性が高い。

### 2. Haiku 呼び出しを行わなかった判断

PRD AC には「`<!-- llm-context: -->` 自動生成は Haiku で」と明記されていたが、`lint.sh --no-llm` 実行時に `section-context-missing` 違反は **0 件** だった（`--no-llm` で検出される範囲内）。Haiku を呼ばずに違反 0 を達成できたため、実装者は Haiku 呼び出しをスキップして PR を作成した。

これは

- 実コスト 0 USD
- 実装速度の高速化
- 不要な LLM 呼び出しを避ける節度

という観点で正しい判断だが、副作用として **LLM 経由 lint（`section-context-check`）のカバレッジ確認が抜けた**。レビュアーはこれを `concern (auto-carveable)` として KMD-145 に退避させ、親 PR をマージ可能扱いにした。AC の N/A 化（「LLM 経由 lint で違反なしのため Haiku 不要」）の判断は妥当だが、その確認自体を別チケットに分離する運用は健全。

### 3. SCHEMA §6「title alias 温存」と双方向性チェック「slug 厳密一致」の整合

SCHEMA §6 ルール 2 は「broken-link 解決時に title alias 温存を許容」する一方、`related-asymmetric` チェック（lint.sh L499-515）は **slug ベースで厳密一致**する。このため d2-diagram-preview / file-tree-outline-sync の Related に残っていた title alias 形式（`[[エディタコア (NSTextViewWrapper)]]`）を slug 形式（`[[editor-core]]`）に置換した。

実装者は d2-diagram-preview.md L103 で `— NSTextView 側の本体（旧表記: エディタコア (NSTextViewWrapper)）` という注釈を残し、可読性損失を最小化した。レビュアーはこれを「丁寧」と評価。

この件は SCHEMA §6 のルール設計が**用途別に異なる挙動を許容している**ことを示す:

- **broken-link 解決**: title alias 温存 OK（既存記事の表記揺れを尊重）
- **related-asymmetric チェック**: slug 厳密一致（双方向性の機械的検証）
- **新規生成・更新**: slug 必須（書き手が判断する余地を残さない）

B 案（title alias）が許容される範囲と、新規生成は slug 必須の境界が運用しやすい設計になっている。

### 4. 大量 docs（11 ファイル）の一括編集リスクと対処

11 ファイル / 32 追加 / 18 削除 という diff サイズは、wiki 記事編集としては大規模。リスクは

- **本文を誤って書き換える**: frontmatter `updated:` と `## Related` セクションだけを触るつもりが、本文 hunk を巻き込む可能性
- **逆方向リンクの不整合を量産**: 双方向性を直すつもりが片方向だけ更新する
- **slug ↔ title alias 置換ミス**: 本文中の参照と Related セクションの参照で表記が割れる

これらは **lint.sh が即座に検出する**ため、「編集 → lint 実行 → violation 確認 → 0 件まで反復」のループで担保された。レビュアーも全 11 ファイルの diff hunk を line-by-line 検証した上で「本文無傷」を確認している。

**学び**: 機械的検証可能な規約があれば、編集量が大きくても安全に進められる。lint.sh が未整備の状態で同じ作業をしていたら数時間かかって違反が残った可能性が高い。KMD-52（lint.sh 実装）→ KMD-53（既存記事適合）の順序が正解だった。

## 良かった点

- **依存順序が綺麗**: KMD-51（SCHEMA 改訂）→ KMD-52（lint 実装）→ KMD-53（記事適合）→ KMD-54（pipeline_weekly 組込）→ KMD-55（ingest gate）と直列に並べた設計が機能した。並行実行を諦める代わりにリワーク 0 回を実現
- **lint.sh による機械的検証**: 14 → 0 の確認を繰り返し可能で、レビュー時間も短縮（PR レビュー自体が 6 分）
- **auto-carve-out が機能**: LLM 経由 lint 未実行という concern を KMD-145 に退避することで、親 PR をブロックせずクリーンな状態で進めた。「人間判断が必要な concern」と「機械的に follow-up できる concern」を分離する設計が回った
- **PR description の構造化**: lint 結果テーブル / 修正カテゴリ別の説明 / title alias → slug 置換の判断理由 / AC 対応リスト、の 4 部構成でレビュアーが追跡しやすい状態だった
- **DocSecurity の自動化**: review_security が markdown 変更でも判定をスキップせず、API キー / トークン / Bearer / 私有鍵パターンをスキャンしたうえで PASS を出している。markdown だけだから安全という暗黙視ではなく明示的に観点を回している点が健全

## 改善点

- **Haiku 呼び出しの記録が AC のままだと N/A 多発**: PRD AC に「Haiku で生成」「実コスト記載」が含まれているが、`--no-llm` 実行で違反 0 になると AC が N/A になる。レビュー時に「AC 達成」と「AC スキップ」が見分けにくい。実装者・レビュアー双方が「N/A の理由」を明示する責務を負ったが、テンプレが無いため自由記述だった
- **エピック完了の自動更新が無い**: KMD-50（親エピック）が 5 子タスク完了後も Todo のまま。子タスクが全部 Done になったら親 issue を自動 Reviewed/Done に進める機構がない。pipeline_active か `kobaamd_archive_done` で対処するか、手動運用とするかの方針が未定義
- **「.md / docs のみの編集は Codex を使わない」が CLAUDE.md に明記されていない**: 今回の判断は合理的だが、規約上はグレー。新しい subagent / 新規 contributor が同じ判断にたどり着けない可能性
- **KMD-52 完了から KMD-53 着手まで 5 分以下**: 同一 pipeline_active サイクル内で連続処理されたが、依存関係（KMD-52 が main にマージされた状態を前提とする lint.sh が必要）を pipeline_active が暗黙的に守れていたかは不明。たまたま順序通り Todo に並んでいたから動いただけかもしれない

## 教訓

- **依存ある子タスク群は直列スケジュールが安全**: 並行実行で工数を縮めるより、SCHEMA → lint → 既存適合 → pipeline 組込の順で逐次実装する方が、リワーク・コンフリクト・規約相互整合の検証コストが下がる。KB2 エピックは 3 日で 5 子タスク完走できた
- **機械的検証ツールを先に作ると後続編集が高速化する**: lint.sh があったから 11 ファイル編集を 15 分で終わらせられた。同じパターンは「format → fix」「test → implement」「validate → migrate」など至るところに適用できる
- **AC が「Haiku で生成」のような実装手段を含むと、必要ない場合の整理が冗長になる**: AC は「結果」を規定し、「手段」はガイドラインに置く方が合理的。本件では「lint violation 0」が真の AC で、Haiku は手段の一つに過ぎない。AC を「lint violation 0、必要に応じて Haiku で section-context 補完」のように書けば N/A の説明負担が消える
- **markdown だけでも security review は走らせる価値がある**: 32 追加行のうち 1 行でも `Authorization: Bearer ...` のような表記が入っていたら本物の漏洩になる。markdown だから安全という前提を持たず、テキスト全件スキャンを習慣化する
- **auto-carve-out は親 PR の「100% 完璧」プレッシャーを下げる**: concern を carveout して別チケットに退避することで、親 PR が遅滞せずに進む。これは「Reviewed/Done を増やす」というパイプライン目標と整合し、検証カバレッジの穴は別 issue として可視化されたまま残るので忘却もしない
