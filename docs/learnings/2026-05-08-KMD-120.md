## 良かった点

- **concern 三分類（rework / auto-carveable / human-judgment）が機能した実例**: review_pr が detected concern 1 件を「動作影響なし・本 PR の AC 範囲外・独立修正可」と判定して KMD-156 に自動退避し、親 PR を `Reviewed` 直行 → `merge_pr` 自動マージへ流せた。`Human in Review` 滞留を回避し、CLAUDE.md ステータスフローの設計意図どおり。
- **AC 解釈の透明開示**: implement_code の Linear コメントが「明示 Read 行が実在したのは create_prd と research_create_ticket の 2 ファイルのみ。残り 3 ファイルは元々無く no-op で、AC は session-context 前提の文言追加 + Constraints 補強として満たした」と PR body / Linear 双方に開示した。AC 4 項目のうち何が done で何が観測項目（次回 postmortem に委譲）かをマッピング表で明示し、レビュアの判断負荷を下げた。
- **review_pr の補足観察が他 subagent への波及作業不要を保証**: review_pr が「review_pr / review_prd / review_security / fix_pr_comments / implement_code / validate_build / improve_prompt / update_wiki / lint_section_context にも明示 Read 行は存在しないことを全件 grep で確認」と書き残しており、後続作業者（次回 postmortem の閲覧者含む）が「残り subagent も漏れなく対応すべきでは？」と再調査する手間を消した。
- **review_security による副次リスクの個別評価**: 「ロール権限拡大なし／Codex 経由鉄則は Constraints 格上げで強化／Linear I/O / Sparkle / post-build / Hardened Runtime 風化リスクなし」と表で評価し、「明示 Read を削るとルールが失われるのでは」という直感的懸念を機械的に却下した。
- **Constraints 格上げによるルール風化への防御策**: 単に明示 Read を削るだけでなく、5 ファイル全ての Constraints セクションで「Swift 実装は必ず Codex CLI 経由」「Sources/ に踏み込む必要が出たら implement_code に差し戻す」「learnings に Action Items として書き implement_code に委ねる」など、各 subagent の責務境界を再明示した。トークン削減と引き換えにルール記憶を弱める懸念に対して PR 内で defense-in-depth を構築した。

## 改善点

- **PRD AC が「明示 Read 行を削除」と書いており、対象 5 ファイルのうち何ファイルに当該行が存在するかを事前確認していなかった**: 実装段階で「3 ファイルは元々無く no-op」と判明。research_create_ticket / create_prd に対する PRD-lite を書いた際、AC が観測前提（実態調査ベース）ではなく仮説前提（5 ファイル全てに明示 Read があるはず）になっていた。事前確認のコストは grep 1 回程度なので、PRD 作成時の標準ステップに「AC 対象ファイルへの該当行存在を grep で実測」を入れる余地がある。
- **frontmatter description の更新漏れ**: implement_code は Workflow 本文の更新に集中し、frontmatter `description:` フィールドの整合まで行き届かなかった。subagent ファイルの構造（frontmatter / Workflow / Constraints / Final Report Format）に対する「変更時の整合性チェックリスト」が implement_code プロンプトに無いため、本文更新時に frontmatter が取り残されやすい。今回は auto-carve で救済されたが、毎回 carve に頼るのではなくチェックリスト化したい。
- **観測項目（KMD-120 自体の postmortem で削減効果を確認）の検証手段が未整備**: PRD AC 4 項目目「次回 postmortem で Karpathy Guidelines / 命名規則違反が発生していないことを確認」「input token 数の削減観測」が test plan に含まれているが、実測する手段（launchd ログから input token を集計するスクリプト等）は本 PR では用意していない。本 postmortem 作成時点でも定量検証ができていない（観測手段を別タスクで整備する必要）。
- **人間承認ゲートでの 2.6 日待ちが支配的**: 実装〜マージは 8 分なのに対し、Backlog 起票から Todo 昇格まで約 2.6 日。pipeline-resilience シリーズの infra 改善は人間承認なしで進められるよう label `pipeline-infra-trusted` のような枠組みを設計する余地がある（ただし安全側に倒すなら現状維持も合理的で、これは人間判断）。

## 教訓

- **AC は「観測 → 文言」の順で書く**: 「対象ファイルから X を削除」のような AC は、対象ファイル群を事前 grep して X の実在件数を確認した上で書くと、実装段階での「実は 2/5 しか該当しなかった」のような透明開示コメントが不要になる。create_prd 時のステップに「AC 対象ファイルへの該当パターン件数を実測してから AC を確定する」を入れる価値がある。
- **明示 Read 行 vs Claude Code 暗黙注入の境界**: subagent プロンプトに `Read CLAUDE.md (always)` のような明示記述があると Claude Code 側で暗黙注入されたコンテキストとは別扱いで再 Read が走り、トークン重複コストになる。今後の subagent 設計では「session context に既に含まれる前提で参照すること（再 Read 不要）」を標準フレーズとして使う。具体的には CLAUDE.md / README.md など Claude Code が自動展開するファイルは明示 Read せず、`Sources/` のように暗黙注入されない一次資料のみピンポイント Read する形に倒す。
- **concern 三分類の意思決定速度**: rework / auto-carveable / human-judgment のうち、auto-carveable に当たるものを review_pr が即時別チケット化することで `Human in Review` 滞留を避けられる。「動作影響なし・AC 範囲外・独立修正可」の 3 条件を全て満たすときは auto-carve、いずれかが欠けるなら rework か human-judgment に倒すという判断ロジックが今回明確に機能した。新規 review_pr のテストケースとして本 PR を参照に置けるレベルの好例。
- **PRD のテストプラン項目が「次回観測する」型のとき、観測手段の整備をセットでチケット化する**: 「次回 postmortem で観測する」と書くだけだと、観測手段（input token 集計スクリプト等）が無いまま postmortem が回ってきて検証不能になる。観測前提の AC を含む PRD は、観測手段の用意を別チケット（または同 PR の影響範囲）として明記する方針にする。
