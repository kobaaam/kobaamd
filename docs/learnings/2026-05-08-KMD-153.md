## 良かった点

- **auto-carve 連鎖が想定どおり機能した**: 親 KMD-150 (PR #74) のレビュー時に「本 PR の goal とは独立した観測性改善」を別チケット化し、親をブロックせず Reviewed 直行 → 独立サイクルで完了。KMD-153 自身のレビューでもさらに「smoke test 自動化」が KMD-171 に carve され、親 PR をブロックしない設計が二段で機能した
- **PRD-lite が AC を 3 件に絞り、実装の発散を防いだ**: 「(1) stdout/stderr 分離 (2) 失敗時 stdout ダンプの既存挙動維持 (3) WARN が呼び出し元 stderr に出ること」の 3 点に限定したため、17 行追加 / 2 行変更で済み、コラテラルダメージなし
- **review_pr の wiki-derived patterns 観点が機能**: security-hardening のクォート規約準拠 / mktemp 使用 / set -e/+e の囲み適切 / err_tmp リーク無し、まで具体的に確認されており、`docs/wiki/articles/practices/security-hardening.md` を Prompt Caching で投入している効果が観測できた
- **review_security が PR diff の性質を正しく認識**: 「観測性回復 (既存 WARN を見えるようにしただけ) であり、新規サイレント失敗予防機構ではないため postmortem-patterns §12 の重い AC は適用範囲外」と判断。観点を盲目的に当てはめず、PR の本質に応じてゲートを選んでいる
- **クリーン APPROVE → Reviewed 直行 → 自動マージ**: `[BREAKING]` なし / concern=0（auto-carve 後）の判定により Human in Review を経由せず、設計どおり「人間に判断を求めるべき余地が無いとき」は AI で完走
- **mock claude を使った smoke test 手動検証**: 成功パス / 失敗パス 両方を mock で確認しており、shell script の挙動変更にしてはテスト戦略がしっかりしている

## 改善点

- **shell script の例外運用に関する明文化が薄い**: CLAUDE.md の役割分担表は「`.swift` ファイルを新規作成・編集するなら → Codex CLI に依頼」と書いているが、shell script (`*.sh`) について明示的な扱いがない。今回 main session が直接 Edit したのは妥当な判断だが、後続の subagent / 人間が判断するための基準が CLAUDE.md / wiki に書かれていないため、再現性のあるルールになっていない
- **smoke test の自動化が手動検証で代替された**: KMD-171 として carve されたが、本来は section-context-check のような「観測機構」自体に shell smoke test を当てる運用基準があれば、初手で test を含めた PR が出せた可能性がある。`postmortem-patterns §12「観測機構の自己観測責務」` の関連項目として、観測機構変更時の test 必須化が議論されていない
- **PR description の「テスト確認」セクションが手動検証ベースに偏った**: `bash -n` 構文チェック / mock claude は最低限であり、CI で回らない。reviewer が「観測性回復という性質と diff サイズから本 PR をブロックすべきでない」と判断したのは妥当だが、テスト戦略が PRD AC の段階で言語化されていれば auto-carve せずに本 PR で対応する選択肢もあった
- **Backlog 滞留 11h30m はパイプラインのサイクル間隔起因**: 10:17 起票後、22:00 まで触られていない。`pipeline_active` の 30 分間隔で考えるとサイクル数は十分ある（22 サイクル分）はずだが、auto-carve された priority Low / `Improvement` ラベル issue は他の WIP に押し負ける運用になっている可能性がある。stale ではないが、優先度設計の観察ポイント

## 教訓

1. **auto-carve は親 PR を守る安全弁として明確に機能している**: 親 PR の goal とは独立な改善（観測性回復・自動テスト追加・UI 磨き込み等）は迷わず carve すべき。本ケースでは KMD-150 → KMD-153 → KMD-171 と二段 carve しても各 PR が surgical で完了している
2. **shell script の小規模 surgical fix（< 30 行）は main session 直接 Edit で十分**: Codex CLI の往復コストが見合わない。CLAUDE.md の役割分担表は「Swift ファイル限定」と読むのが運用上妥当（明文化推奨）
3. **観測機構の変更には観測機構自体の test を求めるべき**: 「観測性回復」という性質の PR では、回帰検出のための smoke test を初手で含めるのが筋。PRD AC に「test 戦略」を 1 行入れるテンプレ調整で防げる
4. **クリーン APPROVE → 直行ルートは AC 限定 + 影響範囲明示で再現できる**: PRD-lite に「影響範囲: scripts/wiki/lib/section-context-check.sh のみ」と明示されていたため、reviewer がコラテラルダメージなしを diff で機械的に確認できた。逆に AC が広い PR では Human in Review 経由が増える
5. **review_security の「PR の本質に応じて適用 AC を選ぶ」判断は wiki-derived 運用の良いパターン**: postmortem-patterns §12 を盲目的に適用せず「適用範囲外」と書いた点は再現したい。観点リストではなく**観点を選ぶ判断ロジック**を wiki 化する価値がある
6. **`pipeline_active` のフェーズ B が初めて 1 サイクルで実装〜マージまで完走**（小規模案件として）: 23 分の能動フェーズ。今後ベンチマーク値として引用できる
