## 良かった点

- **halted リカバリ機構が自己診断として機能した**: pipeline_active が複数サイクルにわたり KMD-117 の halted 状態を正しく検出し、dirty worktree / 権限不足の理由を Linear コメントに残した。人間が状況を把握して手動介入できた。
- **review_pr ラウンド 1 の fail 検出が正確だった**: `ask.sh` の API 切り替えが全呼び出し元を無通告で破壊するコラテラルダメージと、`[BREAKING]` 未付与の 2 点を正確に fail として分類し、concern 4 件を auto-carveable として別チケット（KMD-205〜209）に退避。PRD なし（infra 系）でも影響範囲の観点で深く検出できた。
- **fix_pr_comments の修正が最小かつ的確だった**: ask.sh の revert + lint.sh conflict 解消のみで 2 fail をゼロにし、6 分でラウンド 2 APPROVE を得た。破壊的変更の revert を選択したことで `[BREAKING]` 問題も同時解消。

## 改善点

- **halted リカバリが GitHub write 権限に依存して 4 回連続 blocked された**: `kobaan-bst` アカウントが `kobaaam/kobaamd` への push 権限を持っていないため、`recover_halted.sh --auto` が push ステップで毎回停止。権限チェックを事前に行う仕組みがなく、同じ失敗を 4 回繰り返した。
- **ask.sh の API 切り替えが呼び出し元の更新なしに PR に含まれた**: `ask.sh` は `kobaamd_review_pr` / `kobaamd_review_security` / `kobaamd_create_prd` / `kobaamd_review_prd` の 4 subagent が `ANTHROPIC_API_KEY` 前提で利用する共有インフラスクリプト。Codex が KMD-117 実装中に `ask.sh` を Gemini API に切り替えたが、下流の subagent を同 PR に含めず PR を作成した。レビューで fail として検出されなければそのままマージされていた可能性がある。
- **スコープ外 artifact（docs/talks/, アウトライン.md）が commit に混入した**: halted 中に作業ブランチのワーキングツリーに LT 資料バイナリが蓄積し、32f7d60 コミットにバンドルされた。これは concern としてラウンド 1 で指摘され carve-out されたが、実装エージェントがスコープ管理を自己判断した結果。
- **epic KMD-117 に PRD が存在しない**: infra 系の大規模 epic であっても、PRD がないと `review_pr` が AC を機械検証できず concern 止まりになる。

## 教訓

1. **共有インフラスクリプト（ask.sh 等）の API 切り替えは「全呼び出し元更新を同 PR に含める」か「切り出して別 PR にする」の 2 択のみ許容する**: 呼び出し元を更新せず共有スクリプトの API を変更する commit は、review_pr のコラテラルダメージ検出観点で必ず fail になる。Codex 実装プロンプトに「共有スクリプト変更時は downstream subagent のリスト確認を必須」と明記することで事前に防げる。

2. **halted リカバリの事前条件チェック（push 権限・dirty worktree）を pipeline_active の step 0 に追加する**: 権限不足・dirty worktree で blocked される場合、現在は何度でも同じサイクルで再試行してトークンを浪費する。step 0c の先頭で `git push --dry-run` と `git status --porcelain` を確認し、不通過なら即座に human-intervention コメントを残して skip する制御を追加すべき。

3. **halted ブランチのワーキングツリーには「スコープ外の変更」が蓄積しやすい**: halted 状態が長期化すると作業ブランチ上に無関係な変更が混入する。リカバリ時には `git diff --name-only HEAD` でスコープ外ファイルを必ず確認し、関係なければ別 commit または除外してから PR を作成するフローを recover_halted.sh に組み込む。
