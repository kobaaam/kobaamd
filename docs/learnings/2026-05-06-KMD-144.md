# Postmortem: KMD-144

## サマリ

`kobaamd_update_wiki` の lint ゲートが `scripts/wiki/lint.sh` 不在時に `LINT_STATUS=skipped` で silent に commit を続ける構造的なサイレント失敗リスクと、Final Report Format の `commit:` 行の表記揺れを 1 PR に統合して解消したチケット。`scripts/wiki/ingest_history.sh` を新規追加し、`.logs/wiki_ingest_history.jsonl` に lint_status を append して直近 5 回連続 `skipped`/`error` を検出すると Linear epic KMD-44 に warning コメントを自動投稿する仕組みを導入した。`.claude/agents/kobaamd_update_wiki.md` の Final Report Format も `<>` プレースホルダ形式に揃え、`ingest history:` 行を必須化。Swift 変更なし、bash + markdown のみ。リードタイム同日内、リワーク 0 回、auto-carve-out 1 件（KMD-146）。

## 良かった点

1. **小さく独立した PR スコープ**: 親 PR (KMD-55) の AC を阻害しない 2 件の改善を carve-out 起票で別 PR として処理した結果、レビューが review_pr / review_security の両方で短時間 PASS し、Reviewed 直行で自動マージできた。`scripts/wiki/ingest_history.sh` 追加 + agent prompt 23 行差分 + 既存 step 6 a-e / step 7 / lint 判定への影響なし、という影響範囲が PRD と一致したことが APPROVE 直行の決め手になっている。
2. **bash 安全規約の徹底**: 新規スクリプトの段階で `set -euo pipefail` / `"$VAR"` クォート規約 / allowlist バリデーション (`is_valid_status`, `is_non_negative_integer`) / `mktemp` + `trap cleanup EXIT` / jq の `--arg` `--argjson` 型安全運用が一通り揃っており、review_security が CRITICAL/WARNING ゼロで PASS。`practices/security-hardening.md` のクォート規約と allowlist パターンを Codex プロンプト時点で意識できていた。
3. **2 系統 review の並行運用**: review_pr（機能・PRD AC 整合）と review_security（サプライチェーン / シークレット / コード安全性）が同 commit (`e97e2c2`) を別観点で同時審査し、機能側は concern を auto-carveable に分類、security 側は PASS + LOW 提案で完全に独立判定した。観点を分けたことで「機能 OK だが安全性は要再考」のような境界事例も網羅できる構造が機能した。
4. **auto carve-out フローの実運用成功**: review_pr が「AC は満たすが将来の堅牢性に課題」と判定した concern（trap+local+nounset の unbound variable / malformed JSONL 耐性）を機械的に KMD-146 に分離し、親 PR を block せず Reviewed 直行させた。Human in Review に滞留させずスループットを保ったまま、改善観点を Linear に確実に残せている。
5. **サイレント失敗予防の機構を観測ループ自体に組み込んだ**: lint ゲートが silent に skipped を返す問題を「誰かが気づく」ではなく「履歴を append → 連続検出 → epic に通知」という機械的なフィードバックループに落とした。`practices/security-hardening.md` の「サイレント失敗パターン」表に挙がっていた既知の盲点を具体的なスクリプトに翻訳できた。

## 改善点

1. **新機構自身がサイレント失敗するリスクを設計時点で潰しきれなかった**: review_pr が指摘した通り、`check_cmd()` 内の `local comment_file=""` は `set -u` + `trap cleanup EXIT` の組み合わせで「関数スコープ脱出後に unbound variable 参照」が起こり得る。**サイレント失敗予防のための機構が、自分自身もサイレント失敗する可能性がある**という反転構造で、`practices/security-hardening.md` 表の「検証ロジックが always-pass」の枠そのもの。`HISTORY_REPORT=$(... || true)` のフォールバックでさらに永続的にマスクされる。設計時点で「観測ループ自身の観測性」を AC に含めていれば防げた可能性が高い。KMD-146 として carve-out 済み。
2. **テストカバレッジが happy-path 中心**: PR 説明の sandbox 7 ケースは「ファイルなし / 連続件数 / 末尾 reset / 不正 status / カスタム threshold」とロジック中心で、「lq.sh 不在」「LINEAR_API_KEY 未設定」「Linear API 障害」「malformed JSONL 混入」のリカバリ系シナリオを含んでいなかった。失敗パスを sandbox の常設シナリオに含める習慣がプロンプト側にまだない。
3. **Final Report Format の表記揺れに気づくのが事後的だった**: `commit:` 行の `<>` 形式不揃いは KMD-55 (PR #65) のレビューで初めて指摘された。Final Report Format をテンプレートとして lint できる仕組み（agent prompt 内のフォーマット定義の整合チェック）が現状ない。テンプレート差分が積み重なる前に検出する自動化が将来必要になる。

## 教訓

### パターン 12: サイレント失敗予防機構の自己観測責務

サイレント失敗を予防する機構を新規追加するときは、**その機構自身が同じパターンで死なないことを AC に含める**べき。今回の `ingest_history.sh check` は「lint ゲートの silent skipped を観測ループで掬う」役割だが、機構自身が以下の 3 重で silent fail し得た。

1. `set -u` + `trap cleanup EXIT` + `local var=""` の組み合わせで、cleanup 発火時に `comment_file: unbound variable` で死ぬ
2. 死んだ exit 1 を呼び出し側 `kobaamd_update_wiki` step 6.f が `|| true` でマスクする
3. マスクされた結果 `HISTORY_REPORT=""` となり、`grep -E '^warning='` が空一致して warning 検出機能ごと無声化する

これは `practices/security-hardening.md` の「サイレント失敗パターン」表の「検証ロジックが always-pass」と同型。**観測する側の機構には「観測自体が機能していること」を観測する 1 段上の仕組み（assert / mandatory output schema）が要る**。今回 PR では block しなかったが、KMD-146 で「`HISTORY_REPORT` に `warning=` 行が必ず存在することを呼び出し側で assert する」修正を入れる方針が決まっている。

### パターン 13: 親 PR の auto-carveable concern を統合チケットとして起票する

KMD-55 (PR #65) のレビューで残った改善 2 件（lint_status 観測機構 / Final Report 表記揺れ）を、別個の小チケットではなく「ingest ゲートの観測性とテンプレ整理」という統合チケットとして KMD-144 に集約した。これにより:

- 単独では小さすぎて優先度が上がらない改善が、**意味の塊**として 1 PR で進む
- レビュー観点を統一できる（lint_status 観測 と Final Report Format 整合は「ingest プロセスの可観測性」という同じドメイン）
- carve-out 起票時点で PRD-lite が AC レベルで明確に書かれていたため、実装フェーズで Codex に渡すプロンプトが具体的になりやすかった

ただし、統合する単位を間違えると 1 PR が肥大化する。今回は「同じファイル群（`kobaamd_update_wiki.md` 周辺）に閉じる / 影響範囲が共通 / 同じレビュー観点で見られる」が成立した結果として OK だった。

### パターン 14: APPROVE auto carve-out が成立する 3 条件

review_pr が「APPROVE / Reviewed 直行 / Human in Review を経由しない」と判定するために、KMD-144 の review コメントは以下 3 条件を満たしていた。

1. **PRD AC を完全充足**（3 項目すべて pass）
2. **影響範囲が PRD 記載と一致**（step 6 a-e / step 7 / 既存違反コメント投稿は無傷、と PR コメントで明示）
3. **残 concern が `auto-carveable` 分類のみ**（rework=0, human-judgment=0, auto-carveable=2 → KMD-146 に集約）

逆に言うと、PRD AC 充足が pass でも影響範囲が PRD と乖離しているか、concern が「仕様判断必要」に該当すると Human in Review に入る。auto carve-out で Reviewed 直行を狙うなら、実装段階で「PRD に書かれた影響範囲だけを触る」「CSI 改善は別 issue 起票で残す」を意識すると通りやすい。
