## 良かった点

- **review_pr ↔ fix_pr_comments の 1 ループで rework が完結した**: 「テスト未追加」という単一観点の fail に対し、`fix_pr_comments` が `extractTags(from:)` の 5 系統（frontmatter block list / inline array / inline #tag / heading 除外 / コードフェンス除外 / URL #section 除外）を網羅した 85 行のテストファイルを追加し、2 回目レビューはテスト追加 commit のみを評価して即 APPROVE。**fail の粒度が小さく 1 ループで解消できる場合の理想形**を実演した
- **3 系統 concern の auto-carve が機能した**: Gemini が指摘した UI/UX 6 観点（フィルタ vs 展開・HIG・階層タグ・DisclosureGroup・選択中フィードバック・レイアウト破綻）/ `updateFile` の `Array(tagToFiles.keys)` 全走査の O(N) コスト / 外部ファイル変更未検知（FSEvents 不在）を、親 PR をブロックせず KMD-178 / 179 / 180 に分離。すべて Backlog / priority Low / `Improvement` ラベルで定形格納
- **Codex CLI が 1 回呼び出しで実装本体を完了**: 596 行 / 4 ファイル変更（新規 `TagsViewModel.swift` + `TagsView.swift` + `AppViewModel.swift` 改修 + `SidebarView.swift` 組み込み）を一発で要件充足。Codex 往復のコストが発生せず、レビュー fail もテスト範囲のみに限定された

## 改善点

- **Backlog 滞留 5d 17h（2026-05-03 → 2026-05-09）が長い**: PRD は 2026-05-03 起票だが、ピックされたのは 2026-05-09。`kb-pipeline` ラベル付き / priority Low / 工数 2.0 人日 という条件で他の WIP に押し負けた可能性。`kobaamd_detect_stale` の閾値（現状 N 日）が機能していたかは要確認
- **「単体テスト未追加」が implement_code 段階で防げなかった**: PR の「残課題」セクションに「単体テスト追加 ... は別 issue 化検討余地あり」と書かれており、**実装者自身が「テストは別 issue」と判断していた**。ところが review_pr は「類似機能 `TodoViewModelTests.swift` が 157 行存在」を根拠に fail にしている。**「機能追加と同時にテストを追加するか、明示的に別 issue carve する」のどちらかをルール化していない**ため、実装者と reviewer の判断が食い違った
- **PRD に「テスト戦略」欄がない**: KMD-66 の description には AC / 非ゴール / 影響範囲 / 工数のみで、テスト方針が書かれていない。KMD-153 の learnings でも同じアクションが提案されているが、PRD テンプレートが更新されていない（追跡されていない可能性）
- **Codex 1 回呼び出しで完了したのに「影響範囲」が 2 ファイル増えた**: PRD では新規 2 ファイル（`TagsView.swift` / `TagsViewModel.swift`）のみだったが、`AppViewModel.swift` / `SidebarView.swift` への組み込みが不可避で +2 ファイル。これは PRD 設計時に「組み込みポイント」を抽象化しすぎた結果で、reviewer は問題視しなかったが、PRD-lite の「影響範囲」精度の現状値として記録すべき
- **swift test の実行が CommandLineTools 環境で sustained に動かない**: `validate_build` は PASS だが「テスト件数 0」で実行されており、commit `8252d75` で追加した 85 行のテストが**実環境では実行されていない**可能性が高い。reviewer は新規追加コードを diff で読んで「カバー範囲 5 系統」と評価したが、**実行確認は取れていない**。これは KMD-65 と同じ環境制約として既知だが、テスト追加 PR の信頼性ゲートが弱い
- **Gemini 検証コメントが `<!-- gemini-verification -->` HTML コメントで識別している**: 良い試みだが、本 learnings 作成時に grep で検出する経路がまだ整備されていない。mention の集計や統計化が future 課題

## 教訓

1. **「機能追加 PR にはテストを同時に含める」をデフォルトのルールにすべき**: 「別 issue 化検討余地あり」という曖昧な記述は実装者の逃げ道として機能するが、reviewer は「類似機能のテストカバレッジ」を根拠に fail を出す。`kobaamd_implement_code` のプロンプトに「機能追加（新規 ViewModel / Service）は同 PR で単体テストを追加するのを default、carve するなら明示的に別 issue ID を残す」を強制するのが妥当
2. **1 ループ rework は理想的な学習サンプル**: テスト未追加→追加で 1 ループ完結したのは、fail の粒度が「単一観点」「実装と独立に追加可能」「reviewer が具体的な根拠（類似ファイル 157 行）を提示」の 3 条件を満たしたため。**fail 観点を上記 3 条件に分解できる場合は rework が短く済む**ことを subagent_prompt_design に明文化したい
3. **3 系統 concern を独立 PR に carve する判断は、概念軸の独立性で機能する**: KMD-178（perf）/ 179（UI/UX）/ 180（FSEvents）はいずれも「親 PR と直交する観点軸」（計算量 / UX 設計 / 同期戦略）を持つため自然に分離できた。逆に「テスト未追加」のように親 PR の品質を下げる観点は carve せず rework で扱うのが正解。**carve 判断は『観点軸が直交か』『親 PR の品質を下げるか』の 2 軸で切れる**
4. **Gemini UI/UX 検証は AC 評価と UX 評価を分離して使うのが効く**: 今回 Gemini は「PRD のフィルタ解釈と実装が違う」「両セクション展開時のレイアウト破綻」のように **PRD 仕様の解釈幅** を可視化した。AC を機械的に充足させた実装でも UX 観点で改善余地が見つかるため、「Gemini で UI/UX 検証 → AC 違反は fail / それ以外は concern carve」の二段ゲートは有効
5. **swift test がローカル CI で実行できない環境制約は構造的弱点**: テスト追加 PR で「diff で読んで OK」しか言えない状態は、reviewer の負荷を上げる。Xcode 本体での実行 or GitHub Actions CI 化のいずれかで担保する必要がある
6. **PRD 起票から着手まで 5 日超**: priority Low / `kb-pipeline` ラベルの issue は他 WIP に押し負けやすい。これは KMD-153 でも観察された傾向で、`Improvement` ラベル / priority Low の Backlog issue が長時間滞留する**構造的な優先度ロジックの偏り**として再観測
