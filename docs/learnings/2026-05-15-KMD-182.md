# Postmortem: KMD-182

## サマリ

Sparkle EdDSA 秘密鍵の信頼境界を Keychain から GitHub Secrets に移す infra PR を AI パイプラインが自律実行した。review_pr が REQUEST_CHANGES (fail=4) → APPROVE (fail=0, carve 3) の 1 ループで収束し、5 件の carve-out チケット（KMD-195〜199）を自動起票してクリーンマージ。stdin 経由の秘密鍵注入という設計簡素化が、同時に安全性向上（mktemp + trap の廃止）を達成した点が際立つ。

## 良かった点

- **1 ループ収束**: review_pr が 4 件の FAIL を明確に分類し、fix_pr_comments が 1 回のパスで全件修正。ループ上限 3 回の 1 回目で完了した。指摘が「修正方法の具体例付き」だったため Codex CLI が迷わず対処できた
- **auto carve-out の大量活用（5 件）**: 独立改善 5 件（KMD-195〜199）を自動起票して本流をブロックしなかった。carve の基準（本 PR に closed-loop な影響がなく、独立 PR で自然に扱える）が一貫して機能していた
- **review_security と review_pr の並行実行**: security HIGH 3 件を review_security が先行検出し、review_pr が functional view で carve か fix かを判断。分業が機能した
- **stdin 化の自己完結**: FAIL-3 (秘密鍵ログ漏洩) を stdin 経由 (`--ed-key-file -`) で解決することで、FAIL-4 (mktemp 失敗チェック) も根本解消。設計上の複雑さ削減が安全性向上と一致した
- **security-hardening wiki パターンの実際の適用**: review_security が「設計上の不変条件 #3（解釈系コマンドへの外部入力は形式バリデーション必須）」を参照して `Validate secrets format` ステップ追加を要求。wiki-derived patterns が機能した

## 改善点

- **信頼境界変更の人間承認ゲート欠如**: Sparkle EdDSA 秘密鍵の Keychain → GitHub Secrets 移動は信頼モデルの変更（ローカル Keychain = 物理アクセスが必要、GitHub Secrets = GitHub アカウント侵害で漏洩）。AI が単独でこの判断を行い、人間承認なしに Reviewed 直行した。review_security は HIGH で留めたが、信頼境界変更を含む infra PR に対する `[BREAKING]` 判定基準が曖昧だった
- **carve-out 5 件の粒度判断**: 5 件が全て priority Low / Backlog に入った結果、優先度が上がらず運用上放置リスクがある。KMD-195〜199 は security-adjacent（appcast silent failure、秘密鍵 validate 漏れ等）にもかかわらず、priority が Low のまま。carve の粒度と priority 設定に改善余地がある
- **実動テストの欠如**: `swift build / swift test` は pass だが、GitHub Actions ワークフロー自体のテストは「v タグを push して確認」という手動 Test Plan のみ。CI 初稼働前に `act` 等でローカルテストする AC が PRD に含まれていなかった
- **mktemp + trap パターンが初版実装に含まれていた**: KMD-27 で `mktemp` ベースへの移行を既に security-hardening に記録していたが、Codex CLI の初版実装は同じパターン（mktemp 一時ファイル書き出し）を選んだ。wiki の教訓が Codex CLI のコンテキストに届かなかった

## 教訓

### L1: stdin 経由の秘密鍵注入は「設計簡素化と安全性向上の同時達成」パターン

一時ファイルへの書き出し (`mktemp + trap cleanup EXIT`) は、以下のリスクを内包する複合構造:
- デバッグモード (`set -x`) でのトレースログ漏洩
- mktemp 失敗時の空文字展開による不定動作
- trap の INT/TERM 未対応（job cancel 時に一時ファイルが残る）

`printf '%s' "$SECRET" | command --key-file - "$TARGET"` の stdin 方式はこれを根本から消す。対象コマンドが stdin をサポートしているか確認（`--help` または公式ドキュメント）し、サポート有りなら**迷わず stdin 方式を採用する**。設計が単純になるほど攻撃面が減る典型例。

`kobaamd_implement_code` のプロンプトと Codex CLI への指示テンプレートに「シークレットは stdin 経由 (`--key-file -`) を優先。一時ファイルを作る前に stdin 対応を確認すること」を追記する。

### L2: 信頼境界変更を含む infra PR は `[BREAKING]` 扱いで Human in Review を経由すべき

`[BREAKING]` の既存定義は「public API 削除・メジャー dep 更新・データフォーマット破壊」だが、**セキュリティの信頼境界の変更**（管理主体の移動、認証方法の変更、アクセス権の所在の変更）も同等の影響がある。

今回: Sparkle EdDSA 秘密鍵の管理主体が「ローカル Keychain（物理アクセスが必要）」→「GitHub Secrets（GitHub アカウント侵害で漏洩可）」に変わった。これは **秘密鍵の信頼境界変更** であり、AI が単独で判断・実行してよい事項ではない。

`kobaamd_review_security` のプロンプトに「秘密鍵の管理主体の変更・認証フローの変更・アクセス権の所在の変更は `[BREAKING]` タグを PR タイトルに追記し Human in Review に送る」条件を追記する。

### L3: security HIGH の「マージ進行」運用は条件を明示すべき

現行の `security-hardening.md` は「CRITICAL → マージブロック」のみを明記し、HIGH はグレーゾーンになっている。KMD-182 では HIGH 3 件が carve-out または fix で解消されたため結果的に妥当だったが、「HIGH でも CRITICAL がなければマージ進行」という運用が暗黙になっている。

明示すべき運用規則: HIGH は以下のいずれかで解消されればマージ進行を許可する。
1. 本 PR 内で fix 済み（fix_pr_comments ループ）
2. auto-carveable として別チケット起票済み（独立して対応可能と判断できる）
3. review_security コメントに「INFO: 運用上の対処を要するが CRITICAL 相当ではない」と明記

解消されていない HIGH が残る状態でのマージは `[BREAKING]` 扱いで Human in Review を経由する。

### L4: 大量 carve-out (5 件) 時の priority 設定指針

本 PR の carve-out 5 件は全て security-adjacent（rollback silent failure、秘密鍵 validate 漏れ、sign_update バイナリ決定性）だが、priority Low / Backlog で起票された。security-adjacent な carve は最低 priority Normal (3) にする指針が必要。

`kobaamd_review_pr` のプロンプトに「carve-out チケットの priority 設定基準: security-adjacent な改善（secret 取り扱い・ロールバック・バリデーション漏れ）は priority Normal、UI 改善・observability 強化は priority Low」を追記する。

### L5: wiki の教訓が Codex CLI のコンテキストに届かない構造的問題

`security-hardening.md` の「`mktemp` ベースへの移行」は KMD-27 で記録済みだが、KMD-182 の Codex CLI 初版実装は同じパターンを再発させた。wiki が kobaamd_implement_code（Codex への指示生成）のプロンプトに組み込まれていない、または Codex CLI 自身が wiki の内容を受け取れない構造が根本原因。

対策: `kobaamd_implement_code` が Codex CLI へのプロンプトを生成する際、wiki の security-hardening 記事から「シークレット取り扱い禁止パターン」（mktemp + trap、echo による secret 展開）を必ず付与するセクションを追加する。
