# Postmortem: KMD-151

## サマリ

Hardened Runtime + ad-hoc 署名下で実行中の kobaamd を起動したまま `swift build` した結果、後続の `applicationDidChangeScreenParameters` で未ロードの code page をフォルトインした瞬間に `SIGKILL (Code Signature Invalid)` クラッシュが再現。`scripts/post-build.sh` 冒頭に `pkill -x kobaamd 2>/dev/null || true` を 1 行追加するだけのピンポイント修正で対処。実装〜マージまで 2.5 時間、リワーク 0 回、AI レビュー APPROVE 直行で `Reviewed → Done` を一直線に通過した教科書通りのサイクル。

## 良かった点

- **PRD の AC が手術級に具体化されていた**: 「pkill -x で完全一致」「`|| true` で best-effort」「処理順序（Info.plist 上書き → 公開鍵注入 → codesign）の前に挿入」「docs に 1 行追記」まで、AC が実装手順そのものになっていた。Codex がスコープ外を触りようがない構造で、KMD-20 由来の「影響範囲マップ必須化」（postmortem-patterns パターン 1）が機能した好例。
- **再現クラッシュレポートを PRD に直貼り**: Termination Reason / Launch Time / クラッシュ瞬間のコールスタック（`applicationDidChangeScreenParameters` 配下の SwiftUI graph 更新）まで含めた事実ベースの記述があり、「未ロードの code page を初めてフォルトインした瞬間」という根本原因の特定が研究員プロンプト側で完了済み。実装エージェントは設計判断を一切迫られなかった。
- **wiki の既知の罠が事前に効いた**: sparkle-release.md と postmortem-patterns.md に Hardened Runtime / EdDSA / 影響範囲規約が記載されており、本 issue の研究員 → 起票 → 実装 → レビューの全工程が wiki の不変条件（「Info.plist 上書き → 公開鍵注入 → codesign の順序を変えない」など）に整合した。レビューでもこの順序維持が pass チェックの 1 行として明示されている。
- **レビューが多観点で深掘りされた**: review_pr が 11 観点（PRD AC / 影響範囲 / コラテラル / 破壊的変更 / pkill 安全性 / docs / regression / サイレント失敗 / クォート規約 / 影響範囲マップ準拠 / set -euo 不在）を点検しつつ、race window という潜在的な nit を捕捉した上で「block しない理由」を明文化した。security review も 5 軸（supply-chain / secrets / code-safety / entitlements / build-distribution）で並走し、不変条件の維持を二重チェックできた。
- **Simplicity First の判断が正しく効いた**: AC は `pkill -x` のみで wait loop を要求していない。実装も「シンプルに 1 行 + コメント 3 行」で完結し、再現条件（>24h 後の screen 通知）に対して費用対効果の高い対処になった。

## 改善点

- **race window の存在は実装前に PRD で言及できていなかった**: pkill -x は SIGTERM を送るだけで kobaamd の終了を待たないため、`applicationWillTerminate` 実行中に `cp` が始まれば原理的には同じ SIGKILL を再誘発しうる。レビュー段階で nit/question として浮上したが、PRD の「リスク」節に書かれていれば、起票時点で「wait loop は採用しない理由（実用上 SIGTERM 後数百 ms で code page アクセスが収束する経験則）」を明示できた。研究員プロンプトに「対称な代替案（wait loop / pgrep ループ）を最低 1 つ挙げて、採用 or 不採用の理由を書く」観点が不足。
- **再現条件が「>24 時間後の画面構成変化通知」と特殊**: nit の race window で再発した場合、検出までさらに長時間かかる懸念がある。再発検出のための観測手段（クラッシュレポートの自動収集 / Termination Reason 集計）が用意されておらず、再発時の検知は次回も「人間が偶然踏む」依存。
- **レビューに 1.5h の merge 待ち時間**: Reviewed 状態で 01:29 → 03:02 の 1h33m が経過。`pipeline_active` が 30 分間隔で起動するため、最悪ケースでこの程度の merge ラグは構造的に発生する。本 PR のような「クリーン APPROVE / 1 ファイル数行 / 緊急性の高い hotfix 寄り」のものは、reviewer が APPROVE 直後に merge_pr を発火する fast-path があってもよい（要検討）。

## 教訓

- **post-build script の冒頭は「環境クリーンアップ」のための場所として一般化できる**: post-build はビルド成果物を再構成する責務だが、その前段で「実行中の旧バージョンを止める」「壊れた intermediates を消す」「Sparkle update の途中状態を巻き戻す」のような **副作用無効化処理**を bestevant-effort で挟むのが構造的に妥当。今回の `pkill -x kobaamd 2>/dev/null || true` はその第一例として再利用可能なパターン（他の `scripts/*-build.sh` や `scripts/release/*.sh` でも、対応する実行中プロセスを stop する 1 行を冒頭に置く流用が考えられる）。
- **Hardened Runtime + ad-hoc 署名 + 長期実行プロセスの組み合わせには「未ロード code page の遅延フォルトイン」という固有の罠がある**: Termination Reason `CODESIGNING / Invalid Page` は code signing が破られた瞬間ではなく、**page-in 時に検証失敗**で生じる。よって「クラッシュ時刻」と「ビルド時刻」が大きくズレうる（本件は >24h 経過後）。同類の症状を見たら、まず「ビルド成果物がいつ上書きされたか」「クラッシュしたコードパスが起動後に初めて触られた page か」を疑うのがショートカット。
- **Simplicity First が race window を残しても妥当な場合がある**: 完全対策（wait loop + sleep）と簡易対策（pkill のみ）のトレードオフで、再現確率が極端に低い race を許容して 1 行で済ませる判断は、レビュー時に「不採用理由」を明文で残せば後段で再評価できる。本件は nit/question にその判断ログが残ったので、再発したら別 issue で wait loop 化するルートが既に確保されている。
- **PRD で「再現クラッシュレポート＋根本原因のメンタルモデル」を提供できると、実装〜レビューが激短になる**: 「>24h 後に screen 通知でクラッシュ」「未ロードの code page を初めてフォルトイン」というメンタルモデルが PRD 時点で完成していたため、実装側の設計判断を 0 にできた。研究員エージェントの理想形として、再現条件 + 根本原因 + 対処方針の 3 点セットを PRD に必須化する価値がある。
