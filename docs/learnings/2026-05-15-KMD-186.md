## 教訓

1. **pure refactor（動作変更なし）は「変形の等価性論証」を review_pr の必須観点にすべき**: 通常の PR では「動作変更がある変更が正しいか」を確認するが、純粋リファクタでは逆に「変更が動作に影響していないか」の等価性証明が主要な確認事項。`kobaamd_review_pr` のプロンプトに「動作等価リファクタ検出 → 等価性を before/after の制御フローで論証すること」を明記すると、今回のような quality を再現できる
2. **ac-carve 済みリファクタ issue は PRD-lite の影響範囲が「ファイル 1 件・行数明示」で記述されていると最速サイクルに乗れる**: KMD-186 は「NSTextViewWrapper.swift:147-156 周辺」と行番号まで明示されていたため、Codex CLI が迷わず surgical 変更できた。auto-carve 時の PRD-lite テンプレートに行番号範囲の記載を推奨すると良い
3. **priority Low の auto-carve issue は Backlog 滞留が数日になりえる（設計どおりではある）**: 急ぎでなければ問題ないが、「親 PR マージ後 N 日以内に clean-up したい」ような carve-out の場合は、起票時に priority 3 (Normal) を検討する経路を `kobaamd_carve_concerns` のプロンプトに追加することで対処できる
4. **`MainActor.assumeIsolated` の二重ネストは Swift Concurrency の学習曲線によるパターン**: `queue: .main` クロージャ内で `MainActor.assumeIsolated` を複数回書く冗長パターンは、Swift 6 Strict Concurrency への移行期に初学者が踏みやすい落とし穴。実装プロンプトに「`queue: .main` クロージャ内では `MainActor.assumeIsolated` は 1 回のブロックに統合すること」を追記すると初出から清潔なコードが出やすい
