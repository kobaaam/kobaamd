# Postmortem: KMD-154

## サマリ

「2 経路（legacy / subagent）の判定差分を検証する」という当初 AC で着手したが、検証中に **subagent 経路が KMD-152 の最小権限化 (5 月初頭) 以降ずっと壊れていた**ことを発見し、scope を「バグ修正 + 部分検証 + 残差の carve-out」に shift した事例。バグの実体は Commander.js の variadic option (`--allowedTools <tools...>`) が後続の位置引数 `"$prompt"` まで貪欲に取り込み prompt が空になっていたもの。修正は 1 行（stdin 経由化）で、`run_legacy()` / dispatcher / allowlist / retries は完全保持。当初 AC の完全達成（`ANTHROPIC_API_KEY` 持参環境での 2 経路完走）と CI guard 追加はそれぞれ KMD-173 / KMD-172 に auto-carve され、本 PR はクリーン APPROVE → Reviewed 直行 → 自動マージ。**「観測機構が壊れていることを検出する機構が無かった」というメタな観測性の課題**が浮上した postmortem。

## 良かった点

- **scope shift の判断が surgical fix を成立させた**: 当初 AC「2 経路の判定差分を数値化」を機械的に追求すると、`ANTHROPIC_API_KEY` 持参環境を別途用意する＋検証を完走する＋差分を分析する、と肥大化する。subagent 経路が壊れていた瞬間に「先にバグ修正、当初 AC は別チケット」と判断したことで、PR が `+43/-4` の最小 diff に収まり review が機械的に通った
- **1 行修正の選び方が後続の罠も塞ぐ方向に振れた**: 修正は `claude -p ... "$prompt"` を `printf '%s' "$prompt" | claude -p ...` に変更しただけだが、(a) variadic option 後置のバグを **恒久回避**、(b) `%` 等のフォーマットメタ文字を `printf '%s'` で無害化、(c) prompt が `ps aux` の argv から消える副次的なプライバシー改善、と 3 観点で前進。`--allowedTools` の引数順序を入れ替える別解と比べてリグレッション耐性が高い
- **影響範囲が PR description で明示され reviewer の機械チェックが効いた**: 「変更してはいけない箇所: `run_legacy()` 全体・allowlist 配列・prompt 組み立て・retries ロジック」と明文化したことで、`kobaamd_review_pr` が diff を機械的に walk して保持確認できた。コラテラルダメージ検出が pass で通ったのはこの明示の効果
- **AC 部分達成 + 残差の carve-out が筋を通した**: 環境制約（ANTHROPIC_API_KEY なし）で完全達成不能な部分を曖昧にせず、「subagent 経路 12/19 件で違反 0 を確認」「legacy 経路は別環境で検証」「2 経路差分は KMD-173 に集約」と明示。さらに CI guard 不在を KMD-172 として独立 carve し、本 PR をブロックしない設計通りに動いた
- **`docs/wiki/articles/practices/wiki-reference-policy.md` §1.3 への記録が将来読者に効く**: Commander.js variadic option の罠、KMD-150 → KMD-152 で混入し検出機構が無かったため放置された経緯、修正の根拠（stdin 経由化が恒久回避になる理由）を一箇所に集約。同種バグが起きたとき検索一発で辿れる
- **review_security が「観測機構の引数渡しを stdin に逃がす 1 行 fix」を正しく評価**: postmortem-patterns §12「観測機構の自己観測責務」の重い AC を本 PR には適用せず、引数注入リーク確認とフォーマット文字無害化に絞って PASS 判定。観点を盲目的に当てはめない判断が再び機能

## 改善点

- **観測機構が壊れていることを検出する機構が無かった（最大の構造的課題）**: subagent 経路は KMD-152 のマージ (5 月初頭) から KMD-154 着手 (5 月 8 日) までの **約 1 週間ずっと本番で 0 回も成功していなかった**。にもかかわらず以下の理由で誰も気付かなかった:
  - エラーメッセージ（`Error: Input must be provided either through stdin or as a prompt argument`）が `/dev/null` 相当の場所（subagent stdout/stderr）に消えていた（KMD-153 で stderr 中継が入って初めて見える状態になった）
  - `pipeline_active` のフェーズ B では `kobaamd_lint_section_context` が呼ばれる経路に乗っていなかったため定常実行されていなかった（手動起動でしか叩かれない）
  - lint subagent が「サイレント失敗していること」を別の lint / smoke test が確認していなかった（自己観測が無い）
  これは postmortem-patterns §12「サイレント失敗予防機構の自己観測責務」が想定する古典的な失敗事例
- **CI / 統合テストの不在が 1 週間の検出遅延を生んだ**: KMD-150 で導入された subagent 経路は導入時点では動いていたが、KMD-152 で `--allowedTools` allowlist を追加した PR が **subagent 経路自体を実際に呼ばずに** マージされた。`bash -n` 構文チェックは通る、main session の単発確認も「呼び出しコマンドが組み立てられた」までしか見ない。**実際に `claude -p` を叩いて exit code を確認する smoke test が無い**ため、引数解釈バグが構文では検出できないクラスのものだと顕在化までに最長 1 週間ラグった
- **KMD-152 の PR description / AC に「subagent 経路を実際に 1 件回す smoke test」が含まれていなかった**: `--allowedTools` の最小権限化という性質上、引数解釈の挙動が変わるリスクは事前に予見できた。AC として「`section-context-check.sh` を 1 記事に対して実行し exit 0 を確認」を 1 行入れていれば検出できた。これは PRD テンプレ（`kobaamd_create_prd`）の改善点に直結
- **scope shift の正当化を Linear コメントで明示する運用が定着していない**: 本件は PR description / Linear コメントで「当初 AC からのシフト + 残差の carve-out 計画」を丁寧に書いたが、これは run-time に発見した重要バグだから書いた、というアドホックな判断。`kobaamd_implement_code` のプロンプトに「scope shift を発見したらまず Linear コメントで justify する」を明示的に書くと再現しやすい
- **Backlog → Todo の遷移が 2h30m + Todo → In Progress が 10h41m 滞留**: `priority=4 (Low)` で auto-carve された issue は人間ゲート（priority 引き上げ or `ai-research` ラベル外し）が無い限り `assign_work` に拾われない設計だが、本件は先に `pipeline_active` が 12:47 で拾って Todo に上げている（労務的には人間ゲート相当のサブエージェント介入があった可能性）。auto-carve 由来 issue の優先度設計を観察する材料が一つ増えた

## 教訓

1. **「観測機構の壊れ」を観測する第二層の機構が必要**: lint / smoke / observability スクリプトが本番で正しく動いていることを別ループで確認する仕組み（自己観測）が無いと、サイレント失敗が長期間放置される。本件の 1 週間放置はそのもの。具体策は (a) 既存 lint subagent を `pipeline_active` のフェーズ A 末尾で 1 記事に対して実行して exit code をチェック、(b) `pipeline_weekly` で全 19 記事の subagent 経路完走を回す、(c) CI guard で variadic option 後置パターンを検出（KMD-172）、の三層
2. **CLI ライブラリの引数解釈の癖はコードレビューでは検出しにくい**: Commander.js の variadic option は仕様としては既知だが、shell スクリプト diff 上の `claude -p --allowedTools "${allowed_tools[@]}" "$prompt"` を見て「これは prompt が空になる」と気付くのは難しい。**実際に動かす smoke test を AC に必ず 1 つ含める**しか防御策がない（postmortem-patterns §18「観測機構の変更には smoke test を初手で含める」を観測機構以外にも拡張）
3. **stdin 経由化は variadic option バグの汎用予防策**: `printf '%s' "$prompt" | claude -p ...` のパターンは可変長オプション後置の罠を恒久的に塞ぐ。今後 `claude -p` / `codex exec` / 同種の subprocess CLI で長文 prompt を渡すときは **stdin デフォルト化を規約化**する価値がある
4. **scope shift は「発見した瞬間に Linear で justify」が筋**: 「2 経路差分検証」→「先にバグ修正 + 残差 carve」のシフトは、PR description と Linear コメント (`20cbc381-9048-46c3-b061-cdd83a6a0172`) で根拠が明示されたためレビューが機械的に通った。**最小単位の justify は「(a) 当初 AC, (b) 着手中に発見した阻害要因, (c) シフト後 scope, (d) 残差の処理計画」の 4 点**
5. **auto-carve の二段連鎖（KMD-150 → KMD-154 → KMD-172/173）が安全弁として機能した**: 親 PR が独立改善で肥大化しないよう carve、carve 先 PR がさらに残差を carve、というパターンが KMD-153 に続き 2 件目で再現。`Improvement` ラベル + priority Low の運用は機能している
6. **review_security の「PR の本質に応じて適用 AC を選ぶ」判断が再び機能**: 本件も postmortem-patterns §12「観測機構の自己観測責務」を盲目的に適用せず「引数渡し方法の 1 行 fix なので適用範囲外」と判断。**観点リストではなく観点を選ぶ判断ロジックを wiki に書く**価値が、KMD-153 の learning に続いて再確認された
7. **能動フェーズ 48 分は scope shift があった案件としては優秀**: バグ調査 + 修正 + 検証 + ドキュメント追記 + Linear コメントを含めて 48 分。`pipeline_active` 1 サイクルに収まる。scope shift 不要のものは KMD-153 のように 23 分で済むので、**バグ発見が 1 件混じると +25 分が目安**
