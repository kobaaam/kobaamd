## 良かった点

- **Codex CLI 1 call で AC を充足できる依頼設計**: PRD-lite が「`scripts/usage/log.sh` 新規」「`scripts/usage/check.sh` 新規」「`pipeline_active.md` 5b 追加」「ログ形式 `{ts, api, type, est_tokens}`」「閾値（Claude>100 / Codex>50 / Gemini>30）」「fail-open 設計」と具体度の高い形で書かれていたため、Codex への依頼で構造の発散がなく一発実装で 274 行追加 / 3 行削除に収まった。`kobaamd_implement_code` 側の翻訳負荷も最小
- **fail-soft / fail-open ポリシーが PRD 段階で明文化**: log.sh は「失敗時 stderr warn + exit 0 で親プロセス無影響」、check.sh は「exit 0 / 10 / 2 を厳格分岐」「ログ未存在時は exit 2 → fail-open でフェーズ B 継続」と PRD-lite に書かれており、実装側が逸脱しなかった。`kobaamd_review_security` がこの設計を **「自己観測完結」** として PASS 判定した根拠にもなった
- **observability 機構自身を新設する PR で security-hardening のクォート規約を全面遵守**: `set -euo pipefail` / `jq --arg|--argjson` / 正規表現バリデーション / `^[0-9]+$` での threshold バリデーションが全て揃い、`kobaamd_review_security` が **CRITICAL/WARNING ゼロで PASS**。Wiki Prompt Caching 投入の効果が観測できる
- **review_pr が 3 concern を 1 つの統合チケット KMD-176 に集約 carve**: postmortem-patterns §13 の 3 条件（同一ファイル群 / 同一影響範囲 / 同一ドメイン「usage observability の堅牢化」）を満たすと判定して 1 件に統合。1 件 1 チケット分割を避けた **2 例目の実証**（既出は KMD-55 → KMD-144）。低優先度 Backlog の希薄化を防いだ
- **APPROVE auto carve-out 3 条件を満たし Reviewed 直行**: PRD AC 充足 / 影響範囲一致 / 残 concern が auto-carveable のみ、を満たして人間ゲートを通さず自動マージへ。postmortem-patterns §14 の典型例

- **PR description が AC チェックリストと部分充足の透明開示を両立**: 「subagent 起動時の Claude 記録 / Gemini 直書き curl 計装は別途 KB 改善で拡張余地あり」と書かれており、reviewer が partial 充足を機械的に検出して KMD-176 起票に繋げた

## 改善点

- **PRD AC が「subagent 計装」「Gemini 直書き curl 計装」を含むのに本 PR は部分実装で出された**: PR 本文で透明開示 + auto-carve で救済されたが、本来は PRD-lite の AC を「Codex 経由 / wiki/ask.sh 経由の計装まで（subagent 一括計装は別 issue）」と最初から AC スコープを切るべきだった。AC スコープと実装スコープのズレが auto-carve の主要因（concern 1 件目）。`kobaamd_create_prd` / 親 issue 起票時に「観測対象の網羅範囲を AC 確定段階で grep して件数で書く」運用が抜けていた
- **観測機構の smoke test 自動化が同梱されなかった**: postmortem-patterns §18「観測機構の変更には観測機構自体の smoke test を初手で含める」に該当。PR 本文には「bash -n / 通常時 / 閾値超過 / ログ未存在 / 不正入力 / 空ログ」の手動検証 6 ケースが記録されているが、`scripts/usage/check_test.sh` のような自動 smoke test は KMD-176 に carve された。**KMD-153 → KMD-171 と全く同じパターンの再発** であり、§18 が PRD AC テンプレに反映されていれば防げた
- **`check.sh` の入力堅牢性に穴**: `select(.ts? and .api?)` が空文字 `ts` を通すため、`{"ts":"","api":"claude"}` 形式の破損行が混入すると `fromdateiso8601` が parse error → check.sh 全体が exit 2 → fail-open で Phase B 続行。security-hardening の **「サイレント失敗予防機構の自己観測欠如」** と同型（KMD-144 と同パターンの再発）。usage ゲートが**黙って機能停止する**経路が残っている
- **shell-only PR でも `kobaamd_validate_build` が swift build / test を実行している**: Sources/ への変更がゼロ（`scripts/usage/*.sh`, `scripts/codex/run.sh`, `scripts/wiki/ask.sh`, `.claude/commands/*.md` のみ）にもかかわらず swift build (2.92s) / test (0.43s) を実行。今回は短時間で完了したが、原則として **Sources/ 変更がない PR では swift build を skip し、代わりに `bash -n` / shellcheck を回す**ほうが計算資源を節約できる。逆に「Package.swift / Package.resolved / Resources/ への変更があれば swift build を回す」のが理屈。今回は post-build.sh が「.app バンドル未生成」warn を出した（debug build の想定挙動）も含めて、shell-only PR の検証経路として最適化余地あり
- **Backlog 滞留 ~3 日 7h は親 epic ブレークダウン直後の自然滞留**: 同 epic 子 issue（KMD-125〜127）が先に走り、本件が最後だったため。stale 検知のレンジ内なので問題はないが、`pipeline_active` の WIP=1 設計と epic ブレークダウン issue 群との優先度設計について観察値として残す
- **Linear 起票本文が `工数見積もり: 1.5 人日` だったが実際の能動フェーズは 17 分**: 親 epic ブレークダウン時の見積もりが粗い。shell-only / fail-soft 設計が固まっている案件は分単位で完走するため、見積もり精度を上げると `assign_work` の優先度判定にも効く

## 教訓

1. **shell-only PR は AC が具体的で fail-soft / fail-open ポリシーが明示されていれば Codex 1 call で完走できる**: 274 行追加 / 17 分能動フェーズの実証。`kobaamd_implement_code` への翻訳コストを最小化するため、PRD-lite 段階で「ログ形式 (`{ts, api, type, est_tokens}`)」「exit code 規約 (0/10/2)」「fail-open の境界条件」までを書き切ると一発実装の確率が上がる
2. **「サイレント失敗予防機構の新設」は機構自身が同型の落とし穴に落ちる**: KMD-144 と同パターンの再発（`check.sh` の `select(.ts? and .api?)` が空文字 `ts` で fail-open に倒れる）。**新設する観測機構には、機構自身を「依存コマンド失敗 / 環境変数未設定 / 不正入力」のシナリオで叩く smoke test を初手で AC に書く** ことを `kobaamd_create_prd` / `kobaamd_research_create_ticket` のプロンプトに **明示** したほうがよい（postmortem-patterns §12 / §18 の reinforcement）
3. **統合 carve-out チケットの 3 条件運用が 2 例目で確立**: KMD-55 → KMD-144 に続き、KMD-128 → KMD-176 で同一ファイル群 / 同一影響範囲 / 同一ドメインの 3 条件を満たした 3 件 1 枠の集約が機能。1 件 1 チケット分割よりレビュー単位として優れる、と運用上の信頼が高まった。今後の `kobaamd_review_pr` の挙動として **default 統合運用** に倒してよい
4. **shell-only PR の `validate_build` は最適化余地あり**: 今回は swift build / test を盲目的に実行して PASS したが、Sources/ / Package.swift / Resources/ いずれも変更がない PR では `bash -n` + `shellcheck` 系の検証に倒すのがコスト合理的。ただし「Sources/ 変更ゼロ」の判定を完全自動化できる確証がない場合、現状の `swift build` 一律実行は **保守的な fail-safe として正当化できる**（debug build は数秒で済むため、誤検知より実行コストが低い）。判定ロジックを `kobaamd_validate_build` に追加するかは費用対効果次第
5. **APPROVE auto carve-out 3 条件 + 統合 carve は同サイクル内で連鎖適用できる**: postmortem-patterns §13 + §14 を同時に満たすケースの典型。`kobaamd_review_pr` のロジックを「3 件以上の auto-carveable concern が同ドメインに集まったら統合チケットに集約 → APPROVE 直行」に明示すると、判定の再現性が増す
6. **AC スコープの確定段階で「観測対象の網羅範囲」を grep で件数化する運用は usage 計装にも適用できる**: postmortem-patterns §15「AC は『観測 → 文言』の順で書く」を usage 計装にも適用。「13 subagent + Gemini 直書き curl 4 箇所」のような件数を AC 確定前に grep して、PR スコープを明示的に分割しておけば、partial 充足 → carve というパスを取らずに済んだ可能性
